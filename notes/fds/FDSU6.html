01

Graph Fundamentals & Representation

What a graph actually is, the vocabulary every exam question assumes, the two ways to store a graph in memory — and the running example the rest of the unit is built on.

1.1What is a graph?

Definition — Graph

A graph is a non-linear data structure consisting of a finite set of vertices (also called nodes) and a set of edges that connect pairs of those vertices. Formally, a graph is defined as G = (V, E), where V is the vertex set and E is the edge set.

Two properties make graphs fundamentally different from every structure before them. First, there is no root and no required hierarchy — any vertex may connect to any other, in any pattern. Second, cycles are allowed: you can leave a vertex and come back to it. A tree is best understood as a special case of a graph — connected, acyclic, and with one distinguished root — which means a graph is strictly more general than a tree.

This generality is exactly why graphs exist: they model relationships that don't fit a hierarchy. Road networks, social connections, program flow, and "which hosts on a network can reach which others" are all naturally graph-shaped problems.

Why this matters

Graphs are everywhere: road and flight networks (weighted, for shortest routes), social networks (who follows whom), web pages and hyperlinks, and compiler flow-of-control analysis. And the example we will build on for this entire unit: a small network of hosts, where a directed edge means "from this host, an attacker could pivot to that one."

1.3Core vocabulary — every term you will be tested on

The whole unit runs on precise vocabulary. Learn each term with its picture; the exam will use them without definition.

Adjacent and incident

Vertex w is adjacent to vertex v if there is an edge from v to w. That edge is said to be incident on both v and w — adjacency is a property of two vertices, incidence a property of an edge and a vertex.

Paths and cycles

A path is a sequence of vertices joined by arcs, one after another; its length is the number of arcs in it. A path is simple if no vertex repeats — the single exception allowed is the first vertex also being the last. A simple cycle is a simple path of length ≥ 1 that starts and ends at the same vertex.

Degree, in-degree, out-degree

In a digraph, the out-degree of a vertex counts the arcs leaving it, and the in-degree counts the arcs arriving. Undirected graphs have just one degree — the number of edge ends at that vertex.

Connected graphs and components

A graph is connected if a path exists between every pair of vertices. A connected component is a maximal connected piece — you cannot add one more vertex and stay connected. A disconnected graph splits into two or more components.

Weighted graphs

An edge can carry a label — a cost, distance, or capacity — turning the graph into a weighted graph. Weights do not change connectivity; they change what "best" means (shortest, cheapest, fastest).

1.4Directed, undirected, weighted — the core types

How the edges behave decides the graph's type, and the distinction is about symmetry.

  • Undirected graph. Edges have no direction: if Alice is friends with Bob, Bob is also friends with Alice. An edge (v, w) is an unordered pair — w is adjacent to v exactly when v is adjacent to w. Facebook is the canonical example.
  • Directed graph (digraph). Every edge — called an arc — is an ordered pair (v, w) pointing from a tail vertex v to a head vertex w. Alice can follow Bob while Bob doesn't follow Alice back (Twitter/X, Instagram). Direction matters whenever the relationship isn't symmetric: a one-way flight, or a compromised host that can pivot to another host.
  • Weighted graph. Edges carry a value — a cost, distance or capacity. Vertices are cities; weights are driving times. Any of these can be combined (a weighted digraph is completely normal).

1.6Representation A — the adjacency matrix

Definition — Adjacency matrix

Number the n vertices 1…n and build an n × n matrix A where A[i,j] is true exactly when there is an arc from vertex i to vertex j. A labeled adjacency matrix stores the edge's label (a weight, a cost) at A[i,j] instead of just true/false.

The killer feature is the O(1) edge check: "is there an edge from i to j?" is a single array lookup, no matter how many edges the graph has. For an undirected graph the matrix must be symmetric — A[i,j] and A[j,i] always agree, because every edge is counted in both directions.

The cost of that O(1) lookup is space: storage is Θ(n²) — every one of the n² cells is stored whether or not an edge exists there. Our 7-vertex, 8-arc attack graph uses only 8 of its 49 cells. This is wasteful when the graph is sparse (far fewer than n² edges), and it sets a hard floor on speed: simply reading the whole matrix already costs O(n²), which rules out any algorithm faster than O(n²) that uses this representation.

1.7Representation B — the adjacency list

Definition — Adjacency list

For each vertex i, store a list of the vertices adjacent to i — an array HEAD where HEAD[i] points to i's linked list of neighbours. Storage is proportional to (number of vertices) + (number of arcs), with no wasted space for edges that don't exist.

The trade-off is the mirror image of the matrix: storage is O(n + e) — compact even for very sparse graphs — but the edge check "is there an edge from i to j?" now means scanning i's list, which is O(degree of i) in the worst case, up to O(n). What you get in exchange is the operation traversals actually perform most: visiting all neighbours of a vertex takes time proportional to that vertex's degree, not to n. This is why almost every traversal algorithm in this unit assumes an adjacency list.

 The right choice depends on how dense the graph is and what you do most often.

Rule of thumb

e ≪ n² (sparse) → list. e close to n² (dense) → matrix. Choose a list when the graph is sparse — the common case for real-world networks — and you'll mostly be traversing (exactly BFS and DFS, §2 and §3). Choose a matrix when the graph is dense, or when you need fast, repeated "is there an edge?" queries — exactly what Warshall's algorithm does in §4. Our attack graph is sparse (8 edges out of 49 possible), realistic for BFS/DFS — but we still use its matrix form for Warshall's.

Common mistakes — representations

  • Treating an undirected graph's adjacency matrix as if it need not be symmetric — for undirected graphs, A[i,j] and A[j,i] must always agree.
  • Assuming adjacency-list edge lookup is O(1) — it's O(degree of the vertex), which can be O(n) in the worst case.
  • Forgetting that a sparse graph in matrix form still costs Θ(n²) to even read.

Quick check

If you can name a pair (i, j) where the matrix and the list disagree, one of them was built wrong — they encode the same graph.

Section 1 recap

  • A graph generalizes a tree: vertices and edges, no root required, cycles allowed. Formally G = (V, E).
  • Directed vs. undirected is about whether edges have direction; weighted graphs attach a cost or label to each edge.
  • Adjacency matrix: O(1) edge checks, Θ(n²) space. Adjacency list: O(n + e) space, fast traversal.
  • Our attack graph — 7 hosts, 8 arcs — now shows up in every remaining section.

02

Breadth-First Search

Searching level by level. How a FIFO queue turns "visit everything reachable" into a guarantee of shortest paths.

2.1The problem: visiting every vertex, systematically

Many graph problems boil down to one question: starting from one vertex, which other vertices can we reach, and how? We need a disciplined way to visit every reachable vertex exactly once — without that discipline, a graph with cycles sends us walking in circles forever. Breadth-first search (BFS) is one of the two classic answers; depth-first search (§3) is the other.

2.2The big idea: search broadly before deeply

From the start vertex v, first visit every vertex directly adjacent to v — distance 1. Then every unvisited vertex adjacent to those — distance 2. And so on. The search fans out in expanding rings around the start vertex, finishing an entire distance before moving on to the next.

2.3The engine: a FIFO queue

A queue is First-In-First-Out: vertices are processed in exactly the order they were discovered. The discipline is: mark the start vertex visited and enqueue it. Then repeatedly — dequeue a vertex x, and for each unvisited neighbour y of x, mark it visited and enqueue it.

The one detail exams love

Marking a vertex visited at enqueue time — not at dequeue time — is what stops it from being placed on the queue more than once. A vertex already sitting in the queue has already been marked, so no later vertex can enqueue it again. Get this wrong and your queue grows without bound on cyclic graphs.

Input
A graph G = (V, E) and a start vertex v
Output
Every vertex reachable from v, visited exactly once, plus a BFS spanning tree of tree edges
Data structure
An explicit FIFO queue; a visited[] array
Time
O(n + e) with an adjacency list · O(n²) with a matrix

2.4The algorithm

  1. bfs(v): mark v visited and enqueue it.
  2. While the queue is not empty: dequeue a vertex x.
  3. For each vertex y adjacent to x: if y is unvisited, mark it visited, enqueue it, and record (x, y) as a tree edge.
  4. For a disconnected graph: once the queue empties, scan for any vertex still unvisited and call bfs on it too — repeat until every vertex has been visited once.
bfs.cmark-on-enqueue
void bfs(int start) {
    Queue q;
    enqueue(&q, start);
    mark[start] = VISITED;          // mark AT ENQUEUE time

    while (!isEmpty(&q)) {
        int x = dequeue(&q);
        for (each y adjacent to x)
            if (mark[y] == UNVISITED) {
                mark[y] = VISITED;  // never enqueued twice
                enqueue(&q, y);
            }
    }
}

A direct translation of the idea: a queue of vertices, mark-on-enqueue, one loop. Everything else in this section is analysis of what this loop already achieves.

2.7Why BFS finds shortest paths

The argument is worth reproducing exactly, because it is a favourite theory question:

  1. Every vertex enqueued while processing distance-k vertices is exactly at distance k + 1 from the start — the queue processes vertices in non-decreasing distance order, so BFS can never "skip ahead."
  2. Therefore the first time a vertex is discovered, it is discovered by a shortest possible path — no later, longer path could have reached it first.
  3. Following tree edges backward from any vertex to the start retraces one shortest path, hop by hop.

Applying it: read back through BFS tree edges from DC to WS and you get the fewest-hop route an attacker could take from the foothold to the domain controller.

2.8BFS and cycle detection

Build the BFS spanning forest, then look at every non-tree (cross) edge (x, y). Each cross edge completes a simple cycle together with the tree-edge paths from x and from y back to their closest common ancestor. The test runs in O(n) time — independent of the number of edges — because a graph with n vertices and n or more edges is guaranteed to contain a cycle: once the spanning tree's n − 1 edges are placed, every additional edge must close a loop.

2.9BFS on a disconnected graph

The procedure only visits vertices reachable from the start vertex. If the graph has multiple components, some vertices are never enqueued. The fix is one outer loop: after bfs(v) finishes, scan for any vertex still unvisited and call bfs on it too, repeating until every vertex has been visited. Our attack graph happens to be entirely reachable from WS, so this never triggers in the worked example — but real networks often have isolated segments, and exam graphs often do too.

2.10Time complexity — the reasoning

  1. Each vertex is enqueued at most once (it is marked visited immediately), so the while-loop body runs at most n times.
  2. Each edge (x, y) is examined exactly once — when x is dequeued (or once from each end, for an undirected graph).
  3. Total work: O(n + e) with an adjacency list — the same bound as simply reading the graph once.

2.12Variants of breadth-first search

  • Parallel BFS — distributes the frontier (the current level) across processors/cores, since all vertices at distance k can be processed independently.
  • Bidirectional BFS — runs two searches simultaneously, from the source and from the target; they meet in the middle, dramatically cutting the explored volume for far-apart pairs.
  • Multi-source BFS — enqueues several starting vertices at once (all marked distance 0). It answers "nearest source for every vertex" in a single pass — the foundation of distance maps in grids and networks.

2.13When BFS is the right tool

Use caseWhy BFS fits
Shortest path in an unweighted graphGuaranteed minimum hop-count, by construction

Common mistakes — BFS

  • Marking a vertex visited at dequeue time instead of enqueue time — this lets the same vertex be added to the queue multiple times.
  • Using a stack instead of a queue by accident — that turns BFS into something closer to DFS and breaks the shortest-path guarantee.
  • Forgetting to handle disconnected graphs, silently skipping unreachable vertices.

Quick check

If a vertex appears twice in your queue trace, you marked it visited too late.

Section 2 recap

  • BFS explores level by level using a FIFO queue, marking vertices visited at enqueue time.
  • It runs in O(n + e) with an adjacency list, and guarantees the first path found to any vertex is a shortest path.
  • On the attack graph: BFS from WS finds the shortest exploit path to DC is WS → FS → AUTH → DC.
  • Non-tree edges of a BFS (on a digraph) are cross edges; each one reveals a cycle with the tree paths.

03

Depth-First Search

Going as deep as possible, then backtracking. Recursion in place of a queue — and the four arc types that make DFS the foundation of cycle detection and topological sorting.

3.1Go deep before wide

BFS explores in expanding rings. Depth-first search (DFS) takes the opposite strategy: follow one path as far as it goes, then backtrack. It is often the simplest traversal to implement — a handful of lines of recursion — and it is the foundation for both Warshall's-adjacent ideas and topological sorting (§5). Think of it as a generalization of the preorder traversal of a tree: the same recursive shape, just allowing cycles and multiple parents.

Pick a start vertex v and mark it visited. Then, for each unvisited vertex adjacent to v, recursively search it — fully — before trying v's next neighbour. "Fully" is the key word: we don't move on to v's second neighbour until every vertex reachable through the first neighbour has already been visited. If vertices remain unvisited when we run out of paths, pick a new start vertex and repeat — exactly as with BFS.

3.2Recursion is the stack

Where BFS explicitly manages a queue, DFS's "stack" is just the normal call stack: each recursive call to dfs(w) sits on top of the call that discovered it. Backtracking happens automatically — when dfs(w) returns, control resumes exactly where it left off in the caller, ready to try the next neighbour. This is also why DFS can be rewritten iteratively with an explicit stack, the same trade-off we saw with tree traversals.

Input
A graph G = (V, E) and a start vertex v
Output
Every vertex reachable from v, plus discovery order, finish order and an arc classification
Data structure
Recursion — an implicit stack (explicit stack in the iterative version)
Time
O(n + e) with an adjacency list · O(n²) with a matrix

3.3The algorithm

  1. dfs(v): mark v visited.
  2. For each vertex w adjacent to v (in adjacency-list order): if w is unvisited, recursively call dfs(w).
  3. Once every neighbour has been tried, the call returns — the search of v is complete (v "finishes").
  4. To cover a disconnected graph: call dfs on every vertex still unvisited when its turn comes.
dfs.crecursive
void dfs(int v) {
    mark[v] = VISITED;              // check BEFORE recursing
    for (each w adjacent to v)
        if (mark[w] == UNVISITED)
            dfs(w);                 // dive deeper first
}                                   // return = backtrack

The recursive version is barely longer than the idea itself. Note what is absent: no queue, no explicit bookkeeping of "which vertex to try next" — the call stack remembers it for us.

3.6Classifying arcs: tree, forward, back, cross

When dfs(x) examines an arc x→y, y is either unvisited or already visited — and if visited, its relationship to x in the DFS tree (not in the graph!) decides the type. These four labels are the single most examinable idea in this section.

3.7DFS numbering (dfnumber)

Assign each vertex a number in the order DFS first visits it: dfnumber[v] = count; count = count + 1;. The numbering turns arc classification into a mechanical test:

  • Every descendant of v gets a higher dfnumber than v — so tree and forward arcs always go from a lower number to a higher one.
  • Back arcs go from higher to lower (to an ancestor).
  • Cross arcs also go from higher to lower — but between vertices with no ancestor relationship.

That is how the four arc types can be told apart mechanically, without re-visualising the tree: compare dfnumbers and check ancestry only when the numbers decrease.

3.8Using DFS to test acyclicity

Theorem — cycles and back arcs

A directed graph has a cycle if and only if a DFS of it encounters a back arc.

One direction is immediate: a back arc u→v, where v is an ancestor of u, means the tree path v → … → u plus the arc u→v is itself a cycle. The other direction is the book's argument: suppose G has a cycle, and let v be the vertex on that cycle that received the lowest dfnumber. Consider the arc u→v entering v along the cycle. It cannot be a tree arc (v was already numbered before u tried it — actually v being lowest means every other cycle vertex is numbered above v), it cannot be forward or cross — all of those require dfnumber(u) < dfnumber(v) — so it must be a back arc. Since every cycle forces a back arc and every back arc closes a cycle, the test is exact.

3.9Applying DFS: every reachable compromise

A single DFS from the foothold WS visits every host that is reachable at all — not just the shortest way there, but all of them, along whichever paths the search happens to explore. On our attack graph, every host besides WS is reachable: the whole network is exposed from this one foothold. Where BFS answers "what is the shortest path to each host?", DFS answers "what is the full extent of the compromise?"

3.11Time complexity — the reasoning

  1. dfs(v) is called at most once per vertex — the very first line sets mark[v] = visited, and we only recurse into unvisited vertices.
  2. Each call scans v's entire adjacency list once, so total scanning time is proportional to the sum of all list lengths — O(e).
  3. Overall: O(n + e), identical to BFS — both are, to within a constant factor, just the time to look at every vertex and every edge once.

3.12DFS on disconnected graphs: a forest

Exactly like BFS, a single dfs(v) call only reaches v's connected component (or, for a digraph, whatever v can reach). Repeating dfs on every still-unvisited vertex produces a DFS spanning forest — one tree per component — rather than a single tree. The generalization is clean: everything said about tree / forward / back / cross arcs still applies within each tree of the forest.

3.13DFS order isn't unique

Our trace assumed adjacency lists in a specific order (WS: [FS, WEB], FS: [HR, AUTH], …). A different order gives a different — still perfectly valid — DFS. If WS's list were [WEB, FS] instead of [FS, WEB], DFS would explore the WEB side first: a completely different discovery order and a different set of tree / forward / cross classifications.

What does NOT change

The set of reachable vertices is a property of the graph, not of the traversal order. So is the existence of a back arc (a cycle) — if one DFS finds no back arc, no DFS will. Exam questions exploit this: "is the reachability set affected by adjacency-list order?" — no.

Transitive Closure — Warshall's Algorithm

"Can X eventually reach Y?" — answered for every pair of vertices at once, with three nested loops and one boolean matrix.

4.1The problem: all-pairs reachability

BFS and DFS answer "what is reachable from one starting vertex." Sometimes we want the answer for every pair of vertices, all at once. On our attack graph: not just "can WS reach DC," but a complete table of which host can eventually reach which other host. This all-pairs reachability question is what the transitive closure answers.

4.2Definition

Definition — Transitive closure

Given a digraph's adjacency matrix C, the transitive closure is a matrix A where A[i,j] = 1 exactly when there is a path of length one or more from i to j — not necessarily a direct edge. Equivalently, the transitive closure of G = (V, E) is a new graph G⁺ = (V, E⁺) that contains an edge (u, v) if and only if there is a directed path of any length from u to v in the original graph G.

A path of length 2, 3, or 10 all count — A only records whether i can reach j at all, not how far. Note the length-one-or-more requirement: A[i,i] is 1 only if i sits on an actual cycle back to itself, not automatically.

Key concepts

  • Reachability matrix — the closure is typically represented as a boolean matrix where closure[i][j] = 1 if vertex j is reachable from vertex i, and 0 otherwise.
  • Self-loops — every vertex is commonly considered reachable from itself (the reflexive transitive closure), or a self-loop is added if a cycle exists; see §4.12 for this distinction.
  • Graph powers — mathematically, the transitive closure is the union of all graph powers: G ∪ G² ∪ G³ ∪ … ∪ Gⁿ for a graph with n vertices. G² contains exactly the pairs connected by a path of length 2, G³ length 3, and so on.

4.4Why not just run BFS/DFS from every vertex?

That works! Run BFS (or DFS) starting at each of the n vertices and record everything it reaches. Total time: O(n × (n + e)). Warshall's algorithm takes a different route — O(n³) — by processing the adjacency matrix directly instead of running n separate traversals. For dense graphs (e close to n²), the two bounds end up similar — but Warshall's is dramatically simpler to implement: three nested loops, no queue, no recursion.

4.5The key idea: allow detours through vertex k

Process vertices k = 1, 2, …, n in order. After processing k, A[i,j] is true exactly when i can reach j using only intermediate vertices numbered ≤ k.

  • Before any k is processed (k = 0), no intermediate vertices are allowed at all — exactly the direct edges, our starting matrix C.
  • After k = n, every vertex is allowed as an intermediate stop — which is exactly the full transitive closure.

4.6The recurrence

Warshall's recurrence

Ak[i,j]  =  Ak−1[i,j]  ∨  ( Ak−1[i,k] ∧ Ak−1[k,j] )

"already reachable without using k"  OR  "can get to k, and k can get to j"

Why the formula is correct. There is a path from i to j using only intermediates ≤ k exactly when one of two things holds: (1) there was already such a path using only intermediates ≤ k−1 — vertex k simply isn't needed; or (2) there is a path from i to k (intermediates ≤ k−1) and a path from k to j (intermediates ≤ k−1) — splicing them together through k works, since k itself is now allowed. No other case is possible: if a path uses k, it must arrive at k and leave from k at least once, and splicing at the first arrival and last departure gives exactly case (2).

Why one matrix suffices. The recurrence looks like it needs a fresh matrix Ak at every step — but Ak[i,k] and Ak[k,j] are provably identical to Ak−1[i,k] and Ak−1[k,j]. Intuitively: a path from i to k that is allowed to pass through k itself as an intermediate gains nothing new — k cannot be its own useful detour. So row k and column k never change during step k, and the whole computation updates one matrix in place — no separate copies needed.

warshall.ck is the OUTERMOST loop
void warshall(bool A[N][N]) {
    /* A is initialized to the adjacency matrix C */
    for (int k = 0; k < N; k++)        // allow detours through k
        for (int i = 0; i < N; i++)    // from every source i
            for (int j = 0; j < N; j++)    // to every target j
                if (!A[i][j])
                    A[i][j] = A[i][k] && A[k][j];
}

The if (!A[i][j]) check is just an optimization — OR-ing true with anything stays true, so there is no need to recompute an already-true cell. The walkthrough in words: initialize A to C; for k = 1 to n, for i = 1 to n, for j = 1 to n: if A[i,j] is false, set it to (A[i,k] and A[k,j]).

4.10Time complexity — why O(n³)

Three nested loops, each running n times: k from 1 to n, i from 1 to n, j from 1 to n. The body of the innermost loop does O(1) work — one comparison, maybe one assignment. Total: n × n × n × O(1) = O(n³), independent of how many edges the graph actually has — sparse or dense, Warshall's does the same amount of work.

4.11Floyd-Warshall: the cousin that computes distances

Same three nested loops, different body — instead of boolean reachability, Floyd-Warshall computes all-pairs shortest-path lengths on a weighted graph.

Setup — the dist[ ][ ] matrix

  • dist[i][j] holds the weight of the edge from node i to node j.
  • If there is no direct edge, dist[i][j] = INF (infinity — a large value such as 10⁸).
  • The diagonal entries dist[i][i] = 0 — the distance from a node to itself is zero.
  • The graph may contain negative edge weights, but no negative-weight cycles. Works for directed and undirected weighted graphs.

Floyd-Warshall recurrence

dist[i][j]  ←  min( dist[i][j] ,  dist[i][k] + dist[k][j] )

floyd-warshall (pseudocode)same skeleton as Warshall
for k = 0 .. n-1:            // intermediate vertex
  for i = 0 .. n-1:          // source
    for j = 0 .. n-1:        // destination
      dist[i][j] = min(dist[i][j], dist[i][k] + dist[k][j])

A dense graph has significantly more edges than vertices; a sparse graph has very few. No matter how many edges there are, Floyd-Warshall runs O(V³) — so it is best suited to dense graphs. Common mistakes — Warshall's algorithm

  • Getting the loop order wrong — k must be the outermost loop, since row k and column k must be finalized before they are used to update other rows.
  • Expecting A[i,i] to always be true — it is only true if i is actually on a cycle, per the "length one or more" definition.
  • Confusing Warshall's with Floyd's algorithm — same loop structure, but Floyd computes shortest-path lengths, not just yes/no reachability.

Sanity check

Every direct edge in C should still be a 1 in the final A — the closure only ever adds reachability, never removes it.

A common point of confusion — reflexive closure

Warshall's transitive closure only sets A[i,i] = true if there is an actual path of length ≥ 1 from i back to itself — that is, i lies on a cycle. Some applications instead want the reflexive-transitive closure, where every A[i,i] is set to true by definition (every vertex trivially "reaches" itself via a path of length 0). That is a one-line addition after Warshall's finishes — set the diagonal to 1 — but it is a different, explicit choice, not something the algorithm gives you for free. Exam tip: check which convention the question uses before filling the diagonal.

Section 4 recap

  • Transitive closure answers "can i reach j at all?" for every pair simultaneously.
  • Warshall's builds it by allowing detours through vertex 1, 2, …, n one at a time, updating a single boolean matrix in place: A[i,j] ← A[i,j] ∨ (A[i,k] ∧ A[k,j]).
  • O(n³) time — simple, predictable, and a great fit for dense graphs or small ones like our 7-host attack graph.
  • Floyd-Warshall's cousin: same loops, dist[i][j] = min(dist[i][j], dist[i][k] + dist[k][j]) — all-pairs shortest paths.

Topological Sorting

Putting dependencies in order — DFS postorder and Kahn's in-degree method on directed acyclic graphs.

5.1Ordering tasks with dependencies

A large project often splits into smaller tasks, some of which must happen before others — a course needs its prerequisites completed first; a build step needs its inputs compiled first. Model this as a directed graph: an arc from task X to task Y means "X must happen before Y." We want a single linear sequence that respects every one of these constraints at once.

5.2DAGs — the only graphs this works on

A dag (directed acyclic graph) is a directed graph with no cycles — exactly the acyclicity §3 showed how to test, via the presence or absence of a back arc. Dags sit strictly between trees and general digraphs: more flexible than a tree (a vertex can have multiple parents), but without the free-for-all of cycles.

Definition — Topological sort

A topological sort assigns a linear ordering to the vertices of a dag so that for every arc i→j, i appears before j in the ordering. Every arc, without exception, must point "forward" in the final sequence — never backward.

Why cycles and undirected edges are forbidden:

  • Undirected graph: every edge u–v can be seen as both u→v and v→u, so you can't decide which one should come first.
  • Cyclic graph: if the graph contains the cycle u→v→w→u, then you'd need u before v, v before w, and w before u — impossible to satisfy. A cycle means "X must come before Y, and Y before X," which no linear order can honour.

5.3Two canonical examples

5.4The order is (almost) never unique

Any ordering that satisfies "u before v for every arc u→v" is valid — and there are usually several. Take arcs 4→3, 5→3, 3→1: since nothing orders 4 against 5, both 4, 5, 3, 1 and 5, 4, 3, 1 are correct topological orders. Exams love this: your answer may differ from the marking scheme's and still be perfectly right, as long as every arc points forward.

5.5Method 1 — topological sort via DFS

The idea

Run depth-first search. Every time a call to dfs(v) is about to return — that is, every vertex adjacent to v has been fully explored — write down v. This produces the vertices in reverse topological order: print them, then reverse the list (or push onto a stack and pop them off). One extra line added to the plain DFS template from §3 is all it takes.

Why it works. A dag has no back arcs (§3) — so every non-tree arc leaving a vertex x is a forward or cross arc, and both kinds only ever point to vertices that are already completely finished. So the instant dfs(x) is about to return, every vertex x has an arc to has already been written down — meaning x is written down before all of them in the reverse-order list, and after all of them once we reverse it. That is exactly the topological property: every arc x→y has x appearing before y.

topsort.crecord on finish, then reverse
void topsort(int v, Stack* order) {
    mark[v] = VISITED;
    for (each w adjacent to v)
        if (mark[w] == UNVISITED)
            topsort(w, order);
    push(order, v);   // v is now "finished"
}
/* Popping `order` afterward yields a valid
   topological order. */

The walkthrough: topsort(v) marks v visited; for each unvisited neighbour w it calls topsort(w); after the loop — once every neighbour is fully handled — it records v as finished. Call topsort on every still-unvisited vertex, exactly like plain DFS, to cover a disconnected dag.

5.7Verifying a topological order

A simple checklist you can run on any candidate answer: assign each vertex its position in the proposed order, then check every single arc. For arc i→j, confirm position(i) < position(j). If even one arc fails this, the ordering is invalid. On WS(1), WEB(2), FS(3), AUTH(4), DB(5), DC(6), HR(7): check WS→FS (1<3 ✓), FS→AUTH (3<4 ✓), AUTH→DC (4<6 ✓) … every arc checks out.

Non-uniqueness, on our graph

Our DFS produced WS, WEB, FS, AUTH, DB, DC, HR. A different starting-neighbour order gives an equally valid, different sequence — WS, FS, HR, WEB, AUTH, DB, DC is also valid: check it, every arc still points from an earlier position to a later one. Any order is valid as long as it respects every arc — there is rarely just one right answer.

5.8Method 2 — Kahn's algorithm (BFS-based)

Topological sort using BFS (Kahn's algorithm) works by repeatedly selecting vertices with in-degree zero (no dependencies), adding them to the result, and reducing the in-degree of their adjacent vertices. This continues until all vertices are processed, producing a valid linear ordering of a DAG.

kahn (pseudocode)in-degree peeling
/* 1 */ compute in-degree of every vertex
/* 2 */ enqueue every vertex with in-degree 0
/* 3 */ while queue not empty:
/* 4 */     dequeue x; append x to the order
/* 5 */     for each y adjacent to x:
/* 6 */         in-degree[y] -= 1
/* 7 */         if in-degree[y] == 0: enqueue y
/* 8 */ if order contains all n vertices: valid topo order
/* 9 */ else: the graph has a cycle

Line 9 is a bonus exam favourite: Kahn's doubles as a cycle detector — if the order comes out short, the leftover vertices all sit on (or hang from) a cycle.

5.9Applications, advantages, disadvantages

Advantages & applicationsDisadvantages
  • Task scheduling and project management — e.g. course scheduling in universities
  • Detects cycles in a directed graph — e.g. deadlock detection in operating systems
  • Efficient for solving problems with precedence constraints
  • Software deployment tools like Makefile and other dependency resolvers
  • May not be unique — multiple valid topological orderings can exist
  • Only defined for DAGs — cyclic or undirected graphs have no valid order at all

5.10Time complexity

Topological sort is plain DFS with one O(1) line added — recording the finished vertex — so the asymptotic cost does not change at all: O(n + e), same as DFS itself. Every vertex is visited once, every edge examined once. Reversing the finish-order list at the end costs O(n) more — no change to the overall bound.

5.11What if the graph has a cycle?

Add one arc DC→WS to our attack graph — say, a credential re-used back at the entry point — and no topological order can exist at all.

Common mistakes — topological sort

  • Running it on a graph with a cycle — the algorithm won't crash, but the result is meaningless, since no valid order can exist.
  • Forgetting to reverse the DFS finish order — printing vertices as they finish gives the reverse of a topological order, not the order itself.
  • Assuming the result is unique — it almost never is; any order respecting every arc is equally correct.

Quick check

Test acyclicity (§3) before trusting a topological sort's output.

Section 5 recap

  • A topological sort orders a dag's vertices so every arc points forward — impossible on a graph with a cycle.
  • The DFS method: record each vertex when its call finishes, then reverse the list.
  • Kahn's method: repeatedly take an in-degree-0 vertex and peel it off — and a shortfall reveals a cycle.
  • O(n + e) time, and never unique — any order respecting every arc qualifies.

6.1The attack graph, start to finish

Every section attacked the same 7-host, 8-arc graph from a different angle. Collect the four answers in one place — this juxtaposition is exactly what a "compare the graph algorithms" exam question wants:

6.3The complexity ladder

Why does the representation and algorithm choice from §1 matter financially, not just academically? Take a realistic sparse network: n = 1,000 vertices, e = 3,000 edges (e ≪ n²). Count the elementary steps (log-scale bars):

One BFS or DFS — O(n + e)≈ 4,000 steps
BFS from every vertex — O(n·(n+e))≈ 4,000,000 steps
Warshall's — O(n³)≈ 1,000,000,000 steps

Warshall's is roughly 250,000× slower than a single BFS on this graph — which is exactly why §4 stressed that matrix algorithms suit dense graphs, not sparse ones like this. On a small graph (our 7 hosts) the constant-factor simplicity of three nested loops wins; at scale, it does not.

Problem 6 · Topological sort

Find a valid topological order for: A→B, A→C, B→D, C→D.

Show solution

A, B, C, D — or A, C, B, D. Both respect every arc: A precedes B and C; B and C both precede D; nothing constrains B against C, so they may appear in either order. (Any other answer that passes the position check is also correct.)

Problem 7 · Complexity reasoning

A graph has n = 1,000 vertices and e = 3,000 edges (sparse: e ≪ n²). Roughly how much slower is Warshall's algorithm than a single BFS on this graph?

Show solution
  • BFS: O(n + e) = O(1,000 + 3,000) ≈ 4,000 steps.
  • Warshall's: O(n³) = O(1000³) = 1,000,000,000 steps.
  • Ratio: 10⁹ / 4×10³ = 250,000× slower.

Exactly why §4 stressed that matrix algorithms suit dense graphs, not sparse ones like this.

Answer each in one line — no graph needed.

  1. Which traversal is guaranteed to find shortest paths?
  2. Which arc type in a DFS always signals a cycle?
  3. What does Warshall's algorithm compute?
  4. Why must a graph be acyclic for topological sort to work?
Show solution

  • 2. A back arc.
  • 3. The transitive closure — all-pairs reachability.
  • 4. A cycle would force some vertex to appear both before and after another — no linear order can satisfy that.

8.5The trap list

Every trap in the unit, one line each

  • BFS: mark visited at enqueue, not dequeue — or vertices enter the queue twice.
  • BFS: a queue, not a stack — a stack silently turns it into DFS.
  • Disconnected graphs: restart the traversal on unvisited vertices, or you silently skip components.
  • DFS: forward vs cross is decided by tree ancestry, not by visit time alone.
  • Undirected DFS: no cross edges exist — every non-tree edge is a back edge.
  • Warshall: k outermost — wrong loop order silently gives wrong answers.
  • Warshall: A[i,i] is not automatically 1 — only if i lies on a cycle.
  • Floyd vs Warshall: same loops, different body — min of sums vs boolean OR-AND.
  • Topological sort: reverse the DFS finish order — and only dags have one.
  • Undirected matrix must be symmetric; sparse matrix still costs Θ(n²) to read.
