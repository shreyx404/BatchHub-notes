§ 01

Motivation: why clever beats fast

Same data, same machine, radically different effort — three everyday situations that justify the entire discipline.

1.1Finding a name in a phone book

Say we must find Sumit Roy in a printed phone book of N pages.

  • Method 1 — brute force: check one page at a time (A, B, C, …). It works, but in the worst case it costs N page inspections — and doubling the book doubles the work.
  • Method 2 — halving:
    1. Open the book in the middle.
    2. If “Sumit” comes after the current page, ignore the first half.
    3. Repeat on the remaining half.
    Every step throws away half the candidates: N → N/2 → N/4 → … so only ⌈log₂ N⌉ peeks are needed. A 1024-page book: 10 peeks instead of 1024.

1.2The number-guessing game

  • P1 thinks of a number between 1 and 100; P2 must guess it.
  • Technique 1 — random guessing: usually takes 30–50 attempts.
  • Technique 2 — “higher / lower” hints: each answer halves the interval: 100 → 50 → 25 → 12 → 6 → 3 → 2 → 1. P2 succeeds in at most 7 guesses.

Why exactly 7? After k hints at most ⌈100 / 2ᵏ⌉ candidates remain; we need 2ᵏ ≥ 100, and 2⁶ = 64 < 100 ≤ 128 = 2⁷ — so seven guesses always suffice. This is the same arithmetic that makes every “halving” algorithm logarithmic.

1.3How does Google search billions of pages in under a second?

Google indexes billions of web pages, yet answers in less than a second. Is it because it owns a very fast computer? Something else is going on:

  1. a good algorithm, and
  2. a good data structure — the crawled web is pre-organised so that a query touches only a tiny, relevant slice of the data instead of scanning everything.
KEY INSIGHT — THE FOUR LESSONS OF THIS UNIT
  • Changing the algorithm can dramatically reduce the effort.
  • Good algorithms beat brute force.
  • Method matters more than speed — computers are fast, but smart algorithms matter more.
  • Efficiency comes from the pair algorithm + data structure, never from hardware alone.

A useful intuition to carry through Part III: any process that halves its workload each step gains only one extra step each time the input doubles — that is the entire magic of logarithmic time.

§ 02

Algorithms & programs

The logic layer before the code layer — four definitions, the essential properties, and exactly where an algorithm stops and a program begins.

2.1What is an algorithm? — a formality gradient

Level Definition
Very simple A step-by-step procedure for solving a problem.
Simple A finite sequence of well-defined steps used to solve a problem or perform a task.
Computer science A finite, ordered set of unambiguous instructions that transforms input into the desired output.
Real world Like a recipe — it tells you exactly what steps to follow to achieve a specific result.

An algorithm may be specified in English, as pseudocode, or as a computer program; it takes a set of values as input and produces a value (or set of values) as output. There can be more than one algorithm for the same problem, and one algorithm can be implemented in different languages on different platforms.

2.2Key characteristics

  • Input: has zero or more inputs (input is optional in some cases).
  • Output: produces at least one output.
  • Definiteness: every step is clear and unambiguous.
  • Finiteness: terminates after a finite number of steps.
  • Correctness: solves the intended problem — for every input instance, it halts with the correct output. (For sorting, that includes inputs that are already sorted or contain repeated elements.)
  • Efficiency: economical in time and memory.
  • Effectiveness / generality: each step is basic enough to be carried out, and the method works for the whole class of problems it claims to solve.

Only correct algorithms are worth analysing: an incorrect algorithm might not halt at all on some inputs, or might halt with an answer other than the desired one.

2.3Algorithm vs program

Worked example — largest of three numbers. The algorithm:

LARGEST-OF-THREE · ALGORITHMdesign phase
1. Read three numbers: A, B and C.
2. Compare A and B.
3. Compare the larger of the two with C.
4. Display the largest number.
5. Stop.

The program is these five steps translated into C or Python. An algorithm describes the logic; a program is the implementation of that logic in a programming language.

KEY INSIGHT

Program = Algorithms + Data Structures (Niklaus Wirth). A working program is not good enough: if it runs on a large data set, its running time and memory become the real issues — which is exactly why this unit exists.

§ 03

The need for data structures

“What happens if we store everything in a list?” — WhatsApp, Google, your phone contacts and your browser all answer this question the same way.

3.1The motivating question

Picture years of WhatsApp messages stored as one flat list. Every search for an old message must scan from the beginning; every archive operation shuffles gigabytes. Data volume is huge and access must be fast — the only way to get both is to organise the data. Without data structures, large-scale software is impossible.

DEFINITION — DATA STRUCTURE

A way of organising and storing data so that operations on it can be performed efficiently. It gives shape to raw data: instead of keeping information in random form, a data structure arranges it according to a pattern that supports specific operations.

Abstraction — the key concept. We know what operations can be done, not necessarily how they are done. This matters because it lets us reason at the level of operations while leaving the implementation free to change.

3.2Why we need them — the seven reasons

Need What it means Example
Faster data processing Efficient retrieval and modification A hash table gives near-instant lookup vs scanning a massive unorganised file
Optimised resource management Memory allocated & released intelligently A linked list grows/shrinks with real-time needs — no waste
Algorithm efficiency Algorithms rely on the underlying structure The right structure lowers time & space complexity of the operation
Handling scalability Steady performance under heavy load Poorly structured code becomes exponentially slower as data grows
Representing logical relationships Mimic real-world connections Folder hierarchy → tree; interconnected flight map → graph
Code reusability & clean logic Design once, reuse everywhere A generic stack gives LIFO behaviour to many programs

3.4Choosing the right structure

  • Time vs space trade-offs: a hash table is fast but memory-hungry; a compact array may force expensive scans.
  • Fast access vs flexible size: arrays give instant indexed access but fixed size; linked lists flex but cost O(n) to reach an element.
  • Match operations to their frequency: an array-based list retrieves position i in O(1) while a linked list needs O(n) — but insertion/deletion is far easier on the linked list. Pick the implementation based on how often each operation occurs in the application.
  • Small inputs? If the problem size is always small, ignore efficiency and choose the simplest algorithm.
  • Formal comparison tool: Big-O notation — developed fully in § 12–13.

§ 04

Data · data object · data type

Four rungs on one ladder — each rung adds structure, from raw values to a fully specified type system.

4.1Data

DEFINITION

Data is facts in raw form. When processed, it becomes information. Types: numerical, character, etc.

  • Atomic data: cannot be divided into other meaningful pieces — e.g. 249, "abc".
  • Composite data: can be broken into subfields, each with its own meaning — e.g. an address: house number 249, locality "Kondhwa", city, PIN…

4.2Data object

DEFINITION

A data object is a set of elements / variables. Its instances may or may not be related to each other; the set may be finite or infinite; it may be a variable or a constant.

  • A = {'p', 2, 34, "IT"} — a finite object whose instances are not related.
  • Bank employees — a finite object whose instances are related.
  • The set of natural numbers — an infinite data object.

4.3Data type

DEFINITION

A data type is the basic construct of a programming language referring to the kind of data a variable may hold. Two complementary views: (a) a set of data values with predefined characteristics (storage format, range, operations), and (b) a class of data objects together with the set of operations for creating and manipulating them.

EXAM NUGGET — THE CLASSIC int SPEC

In classic C (16-bit): int occupies 2 bytes, range −32768 to 32767, stored as 2’s complement. (On modern 32/64-bit compilers an int is typically 4 bytes / ±2.1 × 10⁹ — quote the syllabus value when asked.)

§ 05

Abstract data types (ADT)

The most important idea in Part II: specify what a type does, hide how it does it — then change the “how” whenever you like.

5.1Abstraction

DEFINITION — ABSTRACTION

Showing only the essential details of how a data structure is used, while hiding the internal implementation details. Abstraction defines what a data structure does, not how it does it.

An ADT therefore bundles three things: (1) declaration of data, (2) declaration of operations, (3) encapsulation of both — the implementation of the operations stays hidden. We don’t need to know how a car (or a fridge) works to use one: we only need to know which operations it supports and how to invoke them. In Java, an interface is the natural vehicle for describing an ADT.

DEFINITION — ADT

An ADT is a conceptual model that defines a data type solely by its behaviour and allowed operations, completely hiding the underlying implementation — a collection of data (values) plus all the operations on that data. Think of it as a blueprint or interface: what can be performed, not how it is executed or stored.

Core principles:

  • Abstraction — only essentials exposed, details omitted.
  • Encapsulation — data and related operations bundled in one unit.
  • Data independence — you can swap the implementation (array → linked list) without affecting how the rest of the program uses the ADT.

5.2Designing an ADT

An ADT is effective when it models something in the real world — and what it models decides what belongs inside it.

  • Does a car ADT need a method returning the car’s colour? It depends on the purpose: for a police or showroom application — yes; if we only model driving time — the colour method is unnecessary baggage.
  • The features of an object represented in the ADT are the object’s attributes; the actions that become operations of the ADT are the object’s behaviours.

5.3Advantages of ADTs

  • Task separation: ADTs separate one part of a larger programming task from the rest — better structuring and multiple programmers working on one project.
  • Libraries: built wisely, they become reusable code incorporated into many different projects.
  • Avoids redundancy: the bank-queue parable — Approach 1: write a program that simulates one specific bank queue; it can never be reused for any other queue. Approach 2: design a queue ADT that solves any queue problem, place it in a library, let every programmer reuse it.

5.5The anatomy of a formal ADT specification

A formal ADT spec has a value definition (an abstract typedef describing the data) plus operation definitions. Each operation carries:

  • Precondition — the condition that must already hold for the operation to work (e.g. the index being in range).
  • Postcondition — what becomes true after the operation completes; the result after processing.

Example 1 — Date ADT

Representation side ↔ application side: a Date object is applied via operations, and represented internally as (yy, mm, dd) — e.g. 2026, 07, 09.

  • NextDay(d) → the date immediately after d (09-Sept-2025 → 10-Sept-2025)
  • Difference(d1, d2) → days between two dates
  • Compare(d1, d2), DayOfWeek(d)…
  • Note: adding or multiplying two dates directly is meaningless — valid operations are differences and day arithmetic. Adding Date + Date is not an ADT operation; AddDay(Date, 1) style helpers exist, but the canonical “tomorrow” operation is NextDay.

Example 2 — Account ADT

  • Deposit(acc, amount)
  • Withdraw(acc, amount) — precondition: balance ≥ amount (you cannot withdraw more than you hold; the account number being prime or the amount being zero are nonsense conditions)
  • Transfer(acc1, acc2, amount)
  • “Compile” is a language action, not an account behaviour — Deposit / Withdraw / Transfer are the operations.

Example 3 — Circle ADT

  • Data that defines a circle uniquely: radius + centre point. (Radius & colour doesn’t fix position; diameter & circumference are redundant — either alone leaves the circle under-determined; area & perimeter are derived, not defining.)
EXAM NUGGET — CIRCLE ADT ARITHMETIC (π = 22/7)

With radius = 7: Diameter = 2r = 14, Circumference = 2πr = 2·(22/7)·7 = 44, Area = πr² = (22/7)·49 = 154. All three operations are valid ⇒ “all of the above”.

Example 4 — Natural Number ADT (full formal spec)

ADT NATURALNUMBERformal specification

  • Predecessor(n) when n = 0 is not allowed — 0 has no predecessor inside ℕ. Successor, addition and multiplication of naturals are always fine.

Example 5 — Array ADT (preconditions & postconditions)

Conventions: ARRTYPE(ub, eltype) denotes the array data type, where ub = maximum size (an int), eltype = type of each element, and el = an element that can be stored. The abstract typedef states the value definition.

§ 06

Data structures & their classification

The ADT is the promise; the data structure is the delivery — and it can be sliced four independent ways.

6.1What a data structure is

  • The implementation of an ADT — concrete, actual.
  • “The portion of memory allotted for a mathematical model, in which the required data can be arranged in a proper fashion.”
  • “A collection of elements and all the possible operations required for that set of elements.”
  • “A collection (grouping) of simple or structured data types and a set of rules (associations / relationships / operations) for organising and accessing the collection.”
  • An aggregation of atomic and composite data into a defined relationship — the “structure” is precisely that set of rules holding the data together.
  • Examples: array, linked list, hash table, tree, graph.

6.2Dichotomy 1 — primitive vs non-primitive

  • Primitive: structures directly operated upon by machine-level instructions — integers, reals, logical data, character data, pointers and references.
  • Non-primitive: derived from primitive structures — sets of homogeneous or heterogeneous elements: arrays and structures, and everything built above them.

6.3Dichotomy 2 — linear vs non-linear

Linear: a list is an ordered set of items connected by position or a link/pointer — an adjacency relationship: each element has one predecessor and one successor. Frequently used for similar kinds of data.

  • Array & multidimensional array — e.g. arr[] = {1,2,3}; contiguous, index-addressed.
  • Single linked list — traversal in one direction: head → 1 → 2 → 3 → 4 → 5 → 6.
  • Doubly linked list — traversal in both directions: h ⇄ 1 ⇄ 2 ⇄ 3.
  • Stack (LIFO) and Queue (FIFO) — restricted-access lists.

Non-linear: no adjacency between consecutive positions — elements sit in hierarchies or networks.

  • Tree — maintains a hierarchical relationship (file systems, corporate charts, folders).
  • Graph — maintains a random / point-to-point relationship (routing networks, maps, social networks).
  • Hash table — maps key→value through a hash function converting a key into a numeric index; average O(1) insert / delete / lookup.

6.4Dichotomy 3 — static vs dynamic

  • Static: fixed-size memory allocated at creation — e.g. an array. Simple, fast, but rigid.
  • Dynamic: memory allocated as per requirement while running — e.g. a linked list. Grows and shrinks exactly with the data.

6.5Dichotomy 4 — persistent vs ephemeral

  • Persistent: modifications are nondestructive — each modification creates a new version and all versions coexist. Example (per the syllabus): a stack.
  • Ephemeral: a modification destroys the version being modified — history is lost. Example: a queue.
stack S1 = 1 2 3 4 · top = 4

6.6Spotlight: heap & trie

  • Heap: a specialised, tree-based structure that satisfies the heap property (parent ≤ children in a min-heap; ≥ in a max-heap) and is always a complete binary tree. It powers priority queues, gives instant min/max access, and drives heapsort.
  • Trie: a prefix tree that stores strings character-by-character along shared prefixes — the natural engine behind autocomplete and spell-checking.

Operations on data structures

Six verbs describe everything you can do to stored, organised data — learn them with the nuance of where each is cheap or expensive.

Operation Definition Cheap in… Expensive in…
Insertion Adding new data (a new node/element) into the structure Stack/queue ends; linked list at a known node Middle of an array (shifting)
Deletion Removing a node from the structure Stack top, queue front Array middle — may require rearrangement
Traversal Accessing each data item exactly once so the nodes can be processed; also called visiting Arrays — a straightforward walk Trees/graphs — need disciplined patterns (DFS / BFS)
Searching Finding the location of a node for a given key value Hash structures; sorted arrays via binary search Unsorted arrays — full O(n) scan

KEY INSIGHT
  • Traversal, searching, sorting, merging are non-primitive operations — they act on whole collections. Addition, multiplication and assignment are primitive machine-level operations. (Favourite MCQ.)
  • Sorting is not a data structure itself — but the chosen structure determines how sorting is performed and how efficient it is. Access/update is direct in arrays (indexed) but sequential in linked lists.
§ 08

Pseudocode & structured programming

How to write an algorithm down before it becomes code — and why “spaghetti” is an insult.

8.1Pseudocode

DEFINITION

A tool used to define algorithms: part English (description without unnecessary detail) and part structured code (sequence, selection, iteration). It provides a language-independent environment for expressing algorithms.

  • Sequence — steps in order; selection — if/then/else; iteration — while/for.
  • Benefits: write and verify logic before coding; communicate algorithms across languages; analyse complexity without implementation noise.
PSEUDOCODE SAMPLESlanguage-independent
ALGORITHM PairSum(a[], n, z)
  for i = 0 to n-1:
      for j = 0 to n-1:
          if i != j and a[i] + a[j] == z:
              return TRUE
  return FALSE

ALGORITHM ADD(A, B)
  C <- A + B
  return C

8.2Programming concepts — three maturity levels

  1. Non-structured linear programs — “spaghetti code”.
  2. Modular programs — decomposed into independent, reusable modules.
  3. Structured programs — built purely from sequence, selection and iteration constructs.

Spaghetti code is unstructured, difficult-to-maintain source code. It is caused by volatile project requirements, lack of programming style rules, and insufficient ability or experience. Mechanically, a non-structured program uses unstructured jumps to labels or line numbers — the flow of execution may jump to any line. Structured programming replaces this with the disciplined constructs of selection (if/then/else) and repetition (while, for).

Why modularity matters: decomposition lets multiple programmers own separate modules, each independently testable and reusable — the same separation-of-concerns logic that ADTs formalise.

§ 09

Algorithmic efficiency: the big picture

Several algorithms can solve the same problem — which is “best”? Efficiency turns that question into mathematics.

DEFINITION — EFFICIENCY

The rate at which storage / memory or time grows as a function of the input size is called efficiency. It is the measure used to analyse the performance of a program for a particular problem.

  • How much time does the algorithm require?
  • How much space (memory) does it occupy?
  • In general, both depend on the input — typically its size. Efficiency is the most important characteristic of an algorithm: by measuring it, we select the best algorithm for our requirements.

9.1Why analyse? (and why not just run and time it?)

Writing a working program is not good enough — the program may be inefficient, and on a large data set the running time becomes the issue. Analysis lets us predict behaviour for large inputs, enjoy simple measures instead of re-timing after every machine change, and compare algorithms to choose the best.

The naive approach — implement both and race them — has three fatal objections:

  1. How are the algorithms coded? Comparing running times means comparing implementations, which are sensitive to programming style that clouds which algorithm is inherently more efficient.
  2. What computer should we use? We must compare independently of any particular computer.
  3. What data should the program use? Any analysis must be independent of specific data.

Therefore we employ mathematical techniques: first count the significant operations in a solution, then express efficiency with growth functions.

9.2The analytical setting

  • Only correct algorithms are analysed — correct means: for every input instance, it halts with the correct output. Incorrect algorithms might not halt at all, or halt with the wrong answer.
  • Analysis = predicting the resources the algorithm requires: memory, communication bandwidth, and computational time (usually the most important).
  • Factors affecting running time: the computer, the compiler, the algorithm used, and the input (its content and, mainly, its size — e.g. the number of items to sort, or the total elements of two matrices to multiply).
  • Machine model assumed: instructions execute one after another — no concurrent (parallel) operations.

9.3Two pillars — and three intuitions

Algorithmic performance has exactly two aspects: time (instructions take time — how fast?) and space (data structures take space — what structures fit?). Each has its own section next. First, the intuition that input size drives everything:

  • Searching for lost keys in one room vs. all the rooms of a building.
  • Calling 3 friends vs. calling 100 friends.
  • Checking each page of a book vs. opening it at a bookmark.
§ 10

Space complexity

Memory is a function of input size too — and it comes from three places.

DEFINITION

Space complexity is the amount of memory a program requires until its termination, as a function of the input size. Problem-solving requires memory to hold temporary data and final results while the program executes.

Why compute it?

  • To know in advance whether sufficient memory is available.
  • To specify memory needs when the program runs on a multi-user system.
  • It is critical when the program must run with limited resources or handle large inputs.

10.1The three kinds of space a program needs

  • Instruction space — the compiled code.
  • Data space — variables, constants, input data.
  • Stack space — one frame per active function call (locals + return address); recursion multiplies this.

Equivalently, split the footprint into a fixed part (independent of input size: code, constants, simple variables) and a variable part (grows with input: dynamic structures, referenced variables, the recursion stack).

10.2Worked examples

BUBBLE SORT — IN-PLACE, O(1) AUXILIARYC++
void bubbleSort(int arr[], int n) {
    for (int i = 0; i < n - 1; ++i) {
        bool swapped = false;                 // last i elements in place
        for (int j = 0; j < n - i - 1; ++j) {
            if (arr[j] > arr[j+1]) {          // wrong order?
                int temp   = arr[j];          // swap
                arr[j]     = arr[j+1];
                arr[j+1]   = temp;
                swapped    = true;
            }
        }
        if (!swapped) break;                  // already sorted: O(n) best case
    }
}

Only temp, i, j, swapped — a constant number of variables regardless of n ⇒ auxiliary space O(1) (an “in-place” sort). A recursive function, by contrast, pays for the stack: recursive factorial(n) has O(n) space.

§ 11

Time complexity & frequency count

Assume every operation costs a constant c, count how often each line runs, and let the arithmetic speak.

DEFINITION — TIME COMPLEXITY

Time complexity quantifies the amount of time an algorithm takes to run as a function of the length of the input (n) — not the actual execution time on any machine. A valid algorithm takes a finite amount of time; the time required to solve the problem is its time complexity. It captures the relationship between running time and input size.

Why compute it? To estimate how long a program will run, to focus on the parts of the code executed the largest number of times, and to find alternate solutions.

What makes the counting method sound? It measures the order of growth in terms of n — independent of machine and configuration, directly correlated with the input, and able to distinguish two algorithms clearly, without ambiguity.

The frequency count of a statement is the count denoting how many times that particular statement is executed. Summing cost × frequency over all statements yields the total step count.

§ 12

Order of growth

Coefficients lie, exponents don’t — growth rate is the only fair comparison between algorithms.

DEFINITION

For n ≥ some constant and f, g ≥ 0: f(n) grows faster than g(n) if g(n)/f(n) → 0 as n → ∞ (equivalently, f(n)/g(n) → ∞). An algorithm’s proportional time requirement is its growth rate — we compare algorithms by comparing growth rates.

  • Example 1: f(n) = 1000 (constant), g(n) = n + 1. For n > 999, g(n) is always larger — the order of growth of g dominates any constant, however big.
  • Example 2: f(n) = 4n² vs g(n) = 2n + 2000. f has the higher order of growth — it grows quadratically in the input size and must eventually overwhelm the linear g, whatever the constants say.

12.1Finding the order of growth in two moves

  1. Ignore the lower-order terms.
  2. Ignore the multiplicative constants.

4n² + 3n + 100  →  4n²  →  n²

100 n log n + 3n + 100 log n + 2  →  100 n log n  →  n log n

12.2Why constants don’t matter: 7n² vs 2n³

Algorithm A runs in 7n², algorithm B in 2n³. B’s coefficient is smaller — does that help?

n 7n² 2n³ Winner
3 63 54 B (last hurrah of the coefficient)
4 112 128 A
10 700 2 000 A
1000 7 × 10⁶ 2 × 10⁹ A, by ~300×

Past the crossover (n ≈ 3.5), n² beats n³ forever, and the coefficients 7 and 2 never matter again. Hence: to evaluate efficiency, identify the most important part of the running time — the algorithm order — which we define formally with asymptotic notation (§ 13).

12.3The full chain (memorise)

c  <  log log n  <  log n  <  ∛n  <  √n  <  n  <  n log n  <  n²  <  n² log n  <  n³  <  n⁴  <  2ⁿ  <  nⁿ

(c is a constant; n is the input size — 10, 100, 1000, ….) Notice: logarithms beat roots, roots beat linear, linear times log sits between linear and quadratic, and exponentials sit above every polynomial.

12.4Properties of growth-rate functions

  • Ignore low-order terms: O(n³ + 4n² + 3n) = O(n³) — only the highest-order term is kept.
  • Ignore multiplicative constants: O(5n³) = O(n³).
  • Addition combines: O(f(n)) + O(g(n)) = O(f(n) + g(n)) — O(n³) + O(4n²) = O(n³ + 4n²) = O(n³). Similar rules hold for multiplication.
EXAM NUGGET — MATHEMATICAL FACTS

Σi = n(n+1)/2 · Σi² = n(n+1)(2n+1)/6 · N + N/2 + N/4 + … = 2N (geometric) · log(ab) = log a + log b · log(aᵇ) = b·log a · for n ≥ 4, n! > 2ⁿ — exponentials lose only to factorials and nⁿ.

§ 13

Asymptotic notations: O · Ω · Θ

Three mathematical hedges: “never worse than”, “never better than”, “exactly like”.

DEFINITION — PURPOSE

Asymptotic notations describe time and space complexity — the behaviour of a function with respect to the input size n. They measure efficiency without machine-specific constants, without implementing, and without timing programs: mathematical tools for asymptotic analysis, defined on functions whose domain is ℕ = {0, 1, 2, …} — convenient for describing worst-case running time T(n).

13.1Big-O — the upper bound (worst case)

DEFINITION

f(n) = O(g(n)) if positive constants c and n₀ exist such that f(n) ≤ c·g(n) for all n ≥ n₀. Set form: O(g(n)) = { f(n) | ∃ c > 0, n₀, with 0 ≤ f(n) ≤ c·g(n) ∀ n ≥ n₀ }.

g(n) is an upper bound for f(n) — g grows at least as fast. Big-O describes the worst-case running time; it is the most commonly used notation.

Worked mathematics — f(n) = 3n + 2, g(n) = n

We need 3n + 2 ≤ C·n. Choose C = 5 (any larger works): 3n + 2 ≤ 5n holds for all n ≥ 1 (n₀ = 1). Hence 3n + 2 = O(n) — true for n and all larger values. We always pick the tightest nearby bound, so we state O(n), not O(n²) (which is also technically true but loose).

  • T(n) = 2n² + 2n + 1 = O(n²) — the Add_arr step count.
  • Insertion sort: worst case is O(n²).
  • A nested loop i = 1…n, j = 1…n is O(n²).

13.2Ω (Omega) — the lower bound (best case)

DEFINITION

f(n) = Ω(g(n)) if positive constants c and n₀ exist such that f(n) ≥ c·g(n) for all n ≥ n₀. Set form: Ω(g(n)) = { f(n) | ∃ c > 0, n₀, with 0 ≤ c·g(n) ≤ f(n) ∀ n ≥ n₀ }.

Ω sets a function to its lower bound and describes the best-case running time.

Worked mathematics — f(n) = 3n + 2, g(n) = n

We need 3n + 2 ≥ C·n. Choose C = 1, n₀ = 1: 3n + 2 ≥ n always. Hence 3n + 2 = Ω(n) — true against n and anything slower like log n or log log n. Tightest bound again: Ω(n).

13.3Θ (Theta) — the tight bound (average case)

DEFINITION

f(n) = Θ(g(n)) iff positive constants c₁ and c₂ exist such that c₁·g(n) ≤ f(n) ≤ c₂·g(n) for all n ≥ n₀. It combines the lower and upper bounds — the function grows exactly like g(n).

Θ sets the function between its lower and upper bound and is used for the average-case characterisation. It is symmetric: f(n) = Θ(g(n)) ⟺ g(n) = Θ(f(n)).

Worked mathematics — f(n) = 3n + 2

1·n ≤ 3n + 2 ≤ 5·n   (c₁ = 1, c₂ = 5, n₀ = 1)  ⇒  f(n) = Θ(n)

So the same function is simultaneously O(n), Ω(n) and Θ(n) — the three notations describe one reality from three sides.

Notation Formal condition Bound Case described Reading
O (Big-Oh) f(n) ≤ c·g(n), ∀ n ≥ n₀ Upper Worst “never worse than g”
Ω (Omega) f(n) ≥ c·g(n), ∀ n ≥ n₀ Lower Best “never better than g”
Θ (Theta) c₁g(n) ≤ f(n) ≤ c₂g(n) Tight Average “grows exactly like g”
KEY INSIGHT — A NOTATION MCQ, DECODED

f(n) = 560n³ + 3n + 107 and g(n) = 3n³ + 5000n². Ratio f/g → 560/3 as n → ∞ — a positive constant. Whenever the ratio tends to a constant, each is O of the other, and both are Θ(n³): same order, different constants. Answer: “f(n) is O(g(n)) and g(n) is O(f(n)).”

Honest caveats (asked as “does asymptotic analysis always work?”):

  • It ignores constants — two algorithms with the same complexity (1000n log n vs 2n log n) cannot be ranked for practical speed.
  • It focuses on large inputs — which real applications may never see.
  • An asymptotically slower algorithm can outperform a “faster” one on the actual input sizes you meet.

It remains the best general method — a unified language for performance that gives an intuitive idea of expected speed and lets us compare algorithms for the same problem; just remember the constants are hidden.

§ 14

Best, worst & average case

The same algorithm is three algorithms depending on its input — know which one an exam question means.

Case Definition Character
Best The input that requires the least time — looks at the fewest data items; minimum steps executed (e.g. a sort given an already sorted array) Lower bound; “NOT so useful” — rarely used
Worst The input requiring the maximum time — looks at the most items; maximum steps executed Upper bound; a guaranteed limit — the standard choice
Average Run the algorithm many times with random input orderings; the expected number of items examined. Compute probability pᵢ that the input comes from each group, time tᵢ for that group, and take Σ pᵢ·tᵢ Needs a statistical distribution model (e.g. uniform); rarely used because it is hard

Why worst case dominates practice: average-case needs every possible input, its frequency and its time — usually impossible; best-case gives little insight when worst-case can be extremely large; worst-case is easier to derive and yields a useful upper-bound guarantee for software products.

14.1Which algorithms even have cases?

  • No case split at all: Merge Sort performs Θ(n log n) operations in every case — worst, best and average coincide.
  • Quick Sort (pivot chosen as a corner element): worst when the input is already sorted (most unbalanced splits); best when pivots always divide the array into two halves.
  • Insertion Sort: worst when the array is reverse-sorted; best when it is already sorted in output order (the inner while-loop never runs → O(n)).

§ 16

Recursion

A function that calls itself on a smaller instance of the same problem — elegant to write, expensive to run naïvely.

DEFINITION

Recursion is a technique where a function calls itself (directly or indirectly) to solve a smaller instance of the same problem. Every functional recursive algorithm needs two parts: a base case — the halting condition that returns a value directly, preventing infinite loops — and a recursive case — logic that shrinks the problem and calls again, moving closer to the base case.

16.1How it works internally — the call stack

  • Pushing: each call creates a new stack frame (local variables + return address) pushed on the system stack.
  • Execution pause: the caller waits on top of the stack while the inner call processes.
  • Unwinding: when the base case triggers, frames pop off one by one, resolving results in LIFO order.

16.2The three canonical examples

SUM · FACTORIAL · FIBONACCIC++
int sum(int n) {                 // note: more expensive than a loop
    if (n == 0) return 0;        // base case               — O(n) time
    return n + sum(n - 1);       // recursive case          — O(n) stack space
}

int factorial(int n) {
    if (n == 0) return 1;        // base case
    return n * factorial(n - 1); // recursive case
}

int fib(int n) {                 // NAIVE version
    if (n == 0) return 0;        // base cases
    if (n == 1) return 1;
    return fib(n-1) + fib(n-2);  // TWO calls: tree recursion
}

Trace of factorial(3) — watch the expansion then the collapse:

factorial(3) = 3 × factorial(2) = 3 × (2 × factorial(1)) = 3 × (2 × (1 × factorial(0))) = 3 × 2 × 1 × 1 = 6

Drawback of naive Fibonacci: exponential time complexity due to repeated subproblem calls — the same values are recomputed over and over (see the tree below). The sum function, though correct, is also slower than its loop equivalent because every call costs a frame.

16.3The four types of recursion

Type Pattern
Direct A function explicitly calls itself in its own body (factorial, fib).
Indirect A calls B, and B calls A — a cycle of calls.
Tail The recursive call is the absolute final statement executed — allowing compiler optimisation (frame reuse).
Tree The body makes multiple recursive calls, branching like a tree (naive fib).

16.4Recursion inside data structures

  • Trees: Inorder / Preorder / Postorder traversals are cleanest recursive — each subtree is a smaller version of the tree.
  • Graphs: Depth-First Search dives into neighbour nodes recursively before backtracking.
  • Linked lists: a list is a node pointing to a smaller list — recursive searching, printing in reverse, deletion.

§ 17

Tower of Hanoi: full derivation

The exam’s favourite recurrence — three rules, three steps, and a closed form of 2ⁿ − 1.

17.1The problem

Move n disks from a source peg to a destination peg using an auxiliary peg, obeying two rules:

  1. Only one disk can be moved at a time.
  2. No disk may be placed on a smaller disk.

17.2The recursive strategy

  1. Move n − 1 disks from source to the auxiliary peg.
  2. Move the largest disk from source to destination.
  3. Move the n − 1 disks from auxiliary to destination.

17.3Deriving the closed form

Let T(n) be the number of moves for n disks. Strategy 1 + 1 + strategy 3 gives:

T(n) = T(n−1) + 1 + T(n−1)  ⇒  T(n) = 2T(n−1) + 1

Expand step by step:

  1. T(n) = 2T(n−1) + 1
  2. T(n) = 2[2T(n−2) + 1] + 1 = 4T(n−2) + 3
  3. T(n) = 8T(n−3) + 7
  4. pattern: T(n) = 2ᵏ·T(n−k) + (2ᵏ − 1)

Set k = n − 1; the base case is T(1) = 1 (one disk, one move):

T(n) = 2n−1 · 1 + (2n−1 − 1) = 2n−1 + 2n−1 − 1 = 2ⁿ − 1

  • Time complexity: T(n) = O(2ⁿ) — exponential; grows very fast as n increases. (Sanity check: n=3 → 7, n=4 → 15, n=5 → 31.)
  • Space complexity (recursion stack): O(n) — the deepest chain of pending calls is n frames.
  • Folklore: with n = 64 disks at one move per second, the world ends after 2⁶⁴ − 1 ≈ 1.8 × 10¹⁹ moves — about 585 billion years.
§ 18

Memoization & time–space trade-off

Buy speed with memory — the single most reusable idea in algorithm engineering.

18.1The time–space trade-off

DEFINITION

A time–space trade-off is the situation where saving time requires using more memory, or saving memory requires spending more time. General principle: “you can reduce the amount of time an algorithm takes by using more memory (space), and vice versa.”

  • Compressed data vs speed: compression minimises storage, but costs CPU cycles to decompress at run time.
  • Lookup tables vs re-calculation: pre-computing values (e.g. sine/cosine tables) gives instant access but consumes memory; computing on the fly is memory-free but slower.
  • Memoization: store results of subproblems → no recomputation → more space.
  • Caching: keep frequently used results (web pages, files) in RAM for instant loading.
  • Database indexing: indexes speed retrieval dramatically but occupy significant extra disk space.

18.2Memoization

DEFINITION

Memoization (Memory + Optimization) is an optimization technique that speeds up recursive functions by storing the results of expensive function calls and reusing them when the same inputs occur again. Use it when time is more critical than memory.

Why it works: some recursive algorithms (Fibonacci!) recompute the same values many times. Memoization caches previous results: without it — high time complexity and repeated computations; with it — faster, reusing already-computed values. This is top-down dynamic programming.

FIBONACCI WITH MEMOIZATIONC++ · top-down DP
int memo[100];                       // assume n <= 99

int fib(int n) {
    if (n == 0) return 0;            // base cases
    if (n == 1) return 1;

    if (memo[n] != -1)               // CACHE HIT: already computed
        return memo[n];

    memo[n] = fib(n-1) + fib(n-2);   // compute once, store forever
    return memo[n];
}

int main() {
    for (int i = 0; i < 100; i++) memo[i] = -1;   // "not yet computed"
    cout << fib(10);                               // 55
}

21.4Classification in one breath

  • Primitive vs non-primitive: machine-operated (int, real, bool, char, pointer) vs derived (arrays, structures, and above).
  • Linear vs non-linear: adjacency (array, singly/doubly linked list, stack, queue) vs hierarchy/network (tree, graph; hash, heap, trie).
  • Static vs dynamic: fixed memory (array) vs allocated on demand (linked list).
  • Persistent vs ephemeral: versions coexist (stack) vs modification destroys (queue).
  • Operations: insert · delete · traverse · search · sort · merge — all non-primitive.
