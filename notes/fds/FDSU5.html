Section 02

Foundations: Linear vs Non-linear

The fundamental difference

In a linear data structure (array, linked list, stack, queue) elements are arranged in a strict sequence: every element has exactly one predecessor and one successor (except the two ends). The structure can therefore be traversed in a single run, and it can express only a one-to-one relationship between elements. Real information, however, is rarely a flat line — a folder contains many files, one employee has many reports, one operator has two operands. For those one-to-many, many-to-one and many-to-many relationships we need non-linear structures (trees, graphs), where a data element may have any number of predecessors and successors.

Definition of a tree

Definition

A tree is a non-linear, hierarchical data structure consisting of a set of nodes connected by edges, with one distinguished node called the root, such that there is exactly one path from the root to every other node and the edges form no cycle. Every other node belongs to exactly one subtree of the root.

The definition is best understood recursively: a single node by itself is a tree (it is its own root); and if n is a node and T₁, T₂, …, Tₖ are disjoint trees with roots n₁, …, nₖ, then attaching those roots as children of n forms a new tree whose root is n and whose subtrees are T₁ … Tₖ. It is also convenient to allow the null tree — a tree with zero nodes — as the base case that every recursive algorithm leans on. A tree is additionally a special case of a graph: a connected graph with no cycles, having exactly N − 1 edges for N nodes.

Key invariants

A tree with N nodes has exactly N − 1 edges. Between any two nodes there is exactly one path. Remove the root and the remaining subtrees form a forest — a forest is simply a collection of trees.

Why trees? The best of both worlds

Arrays give fast search (binary search on a sorted array) but slow insertion and deletion, because elements must be shifted. Linked lists give fast insertion/deletion (relink two pointers) but slow O(n) search. A balanced search tree combines both advantages: its shape keeps data implicitly ordered, so searching discards half the candidates at each step (like binary search), while its linked nodes let insertion and deletion happen by pointer surgery alone, with no shifting. On top of that, trees are the natural container for anything hierarchical.

Familiar hierarchical examples: a book's table of contents (chapters → sections → subsections), a file system (folders contain files and other folders), an arithmetic expression (operators contain operands), the HTML DOM (<html> is the root, <head> and <body> are its children), organisation charts, family genealogy, DNS domain hierarchy, and a compiler's parse of your source code.

Advantages & disadvantages

Advantages
  • Efficient searching — O(log n) in balanced BSTs (AVL, Red-Black); also supports floor/ceiling and sorted traversal, which hashing cannot.
  • Fast insert & delete — O(log n) with self-balancing trees; no element shifting.
  • Natural hierarchy — models containment directly (files, org charts, taxonomies).
  • Recursive structure — trivially traversed and manipulated with short recursive algorithms.
  • Dynamic size — grows and shrinks node by node, unlike fixed arrays.
Disadvantages
  • Memory overhead — every node stores child pointers (2 per binary node).
  • Imbalance risk — an unbalanced tree degrades to O(n) operations (a linked list in disguise).
  • Complexity — trickier to implement and debug than arrays/lists; deletion has corner cases.
  • Hash tables beat trees when you need only search/insert/delete — but trees win as soon as you need ordering, floor, ceiling or sorted output.

The left-to-right ordering rule

Any two nodes that are not in ancestor/descendant relation can still be compared: trace the paths from the root to each; whichever path branches off further left is "to the left of" the other, and everything below it moves with it. On Fig 3.1, node 8 is to the right of node 2 but to the left of nodes 6 and 10 — and it is neither left nor right of its own ancestors 1, 3, 5. This convention is what makes "left subtree before right subtree" meaningful in every traversal.

Counting properties you must memorise

edges = N − 1  ·  max nodes on level i = 2i  ·  max nodes of height h = 2h+1 − 1  ·  min nodes of height h = h + 1
  • N − 1 edges: every node except the root is pointed to by exactly one edge — count the non-root nodes.
  • 2i on level i: each level's nodes can at most double, because each node has at most 2 children (binary case).
  • 2h+1 − 1 total: summing the geometric series 2⁰ + 2¹ + … + 2ʰ gives 2h+1 − 1 (proved rigorously in Practice 14.6).
  • n nodes ⇒ min height ⌊log₂ n⌋, max height n − 1. A perfectly packed tree gains a level only when n doubles; a path-shaped tree wastes none of its height budget.
Convention alert — read this twice

Some textbooks (and parts of this course's slides) count height/levels from 1 (root at level 1). Under that convention the same facts read: max nodes = 2H − 1 for H levels, min height = log₂N + 1, max height = N. The mathematics is identical; only the offset differs. In an exam, state your convention in one line ("height = number of edges, root at height 0") and every marker will follow you.

Common mistakes
  • Depth vs height reversed. Depth is measured down from the root; height is measured up from the node to its farthest leaf. They agree only for the root.
  • Parent ≠ ancestor. Every parent is an ancestor, but an ancestor may be many levels up.
  • Inclusive definitions. Unless the question says "proper", a node is its own ancestor and its own descendant.
  • Level ≠ height. The root is at level 0 but has height equal to the whole tree's height.
Section 04

Binary Trees: Types, Shapes & Representation

What makes a tree "binary"

Definition

A binary tree is either empty, or it consists of a root node together with a left subtree and a right subtree, each of which is itself a binary tree. Every node has 0, 1 or at most 2 children — and a single child is explicitly a left child or a right child.

Two details of this definition carry enormous weight. First, the empty tree is a valid binary tree — it is the base case every recursive algorithm relies on; code that forgets to test NULL crashes at the first leaf. Second, position matters, not just count: a node with only a right child is structurally different from a node with only a left child. In a general (ordered) tree the two shapes below would be the same tree; as binary trees they are different objects, and their traversals differ.

The four canonical shapes

Shape controls height, and height controls the running time of nearly every tree operation. Four adjectives classify binary-tree shapes; a tree can be more than one at once (see the relationship box below).

More precise statements. A tree is full (strictly binary) when every non-leaf node has a non-empty left and right subtree — equivalently, no node has exactly one child. Counting argument worth memorising: if a strictly binary tree has n internal (2-child) nodes it has exactly n + 1 leaves and 2n + 1 total nodes (always odd). A complete tree of height h has between 2h and 2h+1 − 1 nodes. A left-skewed tree has only left branches; a right-skewed tree only right branches.

Relationships — quick test
  • Perfect ⇒ complete and perfect ⇒ full (perfect is the intersection).
  • Full ⇏ complete: a full tree can have an unbalanced last level.
  • Complete ⇏ full: Fig 4.1's complete example has node 3 with exactly one child.
  • Slide decks sometimes say "strictly binary is always complete" — check both rules separately; that claim is not reliable. A tree with 0 or 2 children everywhere can still leave gaps in its last level.

Balance

A binary tree is called balanced when for every node the balance factor = |height(left subtree) − height(right subtree)| is kept small (AVL trees enforce ≤ 1). Balance is what guarantees the O(log n) behaviour that makes search trees useful; a skewed tree has balance factors as large as n−1 and delivers O(n) everything.

Why the shape matters

Search, insert, delete and traversal each do O(height) work along a single path. A perfect/complete tree of n nodes has height only ⌊log₂ n⌋ — doubling n adds just one level. A skewed tree of n nodes has height n − 1 — no better than a plain linked list. Same code, wildly different speed.

Representation 1 — Array (sequential)

Store nodes level by level, left to right, starting with the root at index 0 (the slides use 1-based numbering: root at position 1). The magic is that parent/child positions become arithmetic — no pointers needed:

0-indexed:  left(i) = 2i+1  ·  right(i) = 2i+2  ·  parent(i) = ⌊(i−1)/2⌋
1-indexed:  left(i) = 2i     ·  right(i) = 2i+1  ·  parent(i) = ⌊i/2⌋
Convention alert

The course slide sheet mixes the two conventions (root "stored in the first location" but children at 2i+1 / 2i+2). Treat the 0-indexed triple above as the standard; if a slide uses PARENT(i) = ⌊i/2⌋ − 1 with 1-indexed storage it is the same idea shifted by one. Always test a formula on a 2-level tree before trusting it.

Verification of the formulas on Fig 4.2: node B sits at index 1, so its children are 2·1+1 = 3 (C) and 2·1+2 = 4 (D); node E at index 2 has children 5 (F) and 6 (G); the parent of index 3 is ⌊(3−1)/2⌋ = 1 — exactly B. Seven nodes fill indices 0…6 with no gaps because the tree is complete.

Disadvantages of array representation (list them in exams)
  1. Useful only for complete / full trees — that is where indices stay dense.
  2. For any other shape, most array entries stay empty — a skewed tree of n nodes would still reserve 2n slots in the worst case.
  3. Space is wasted even for mildly incomplete trees.
  4. Inherits all drawbacks of sequential representation (fixed capacity, contiguous memory).
  5. Insertion/deletion needs data movement of many nodes to preserve the index scheme.

Conclusion the slides draw: prefer linked representation. Arrays do, however, remain perfect for heaps (Section 11) precisely because heaps are always complete.

Representation 2 — Linked (dynamic)

Each node is a dynamically allocated structure holding its data plus two pointers. Memory is allocated node by node, the tree can take any shape, and insertion/deletion is pure pointer work. The one thing the linked form does not give you is the parent — if your algorithm needs upward moves (e.g. iterators), add a fourth parent field.

node structure & constructor — C
struct treenode {
    /* data field of any type */
    /* e.g. */ int data;
    struct treenode *lchild;
    struct treenode *rchild;
};

struct treenode* makeNode(int v) {
    struct treenode *n = malloc(sizeof(struct treenode));
    n->data  = v;
    n->lchild = NULL;          /* empty tree = valid base case */
    n->rchild = NULL;
    return n;
}

Converting a general tree → binary tree (Left-Child Right-Sibling)

Any general tree can be stored inside binary nodes, because two pointers are enough: point left at the node's first child, and point right at the node's next sibling. The procedure:

  1. Keep the root of the general tree as the root of the binary tree.
  2. For every node: connect its first child as the left child in the binary tree.
  3. Connect each node's next sibling (same parent, immediately to its right) as the right child.
  4. Recurse until every original edge is represented exactly once.

Facts examiners love: (1) the converted binary tree's root never has a right child (the root of a tree has no siblings); (2) converting a forest works the same way after linking the forest's roots together as siblings — they become one right spine; (3) the original tree can always be recovered by reversing the two rules, so the conversion is lossless.

Ways to build a binary tree

The decks demonstrate five construction styles. The first two below are general-purpose (any shape); the rest are specialist routes covered in their own sections: level-wise insertion suits array representations (§04), expression trees grow from postfix strings (§08), and two-traversal reconstruction is Section 06.8.

Method A — recursive creation with a sentinel (preorder style)

The function asks for a value; entering −1 means "no node here" (a NULL). Because the recursive calls happen after reading the current node, the tree is built in preorder: node first, then its whole left subtree, then its whole right subtree. Walk the sample input on paper once — it is the fastest way to understand how NULLs carve out arbitrary shapes.

create_recursive.c — sentinel −1 = NULL
node* create1() {
    node *p;
    int x;
    printf("Enter data (-1 for no node): ");
    scanf("%d", &x);
    if (x == -1)
        return NULL;              /* base case: empty subtree */
    p = new node(x);              /* make the node FIRST (preorder) */
    printf("Left child of %d:\n", x);
    p->left  = create1();         /* build whole left subtree  */
    printf("Right child of %d:\n", x);
    p->right = create1();         /* build whole right subtree */
    return p;
}
void create() { root = create1(); }   /* public wrapper */

Method C — level-wise insertion (array-flavoured)

Insert new values into the first available NULL slot, scanning levels left to right with a queue — this keeps the tree complete, which is exactly what array representation and heaps require. The queue holds "parents with vacancies"; each dequeue offers its left slot, then its right, then re-enqueues its children for the next round.

Section 06

Tree Traversals — Recursive & Non-recursive

A traversal visits every node exactly once. Unlike an array, a tree has no single natural reading order — and the order you choose changes the meaning of the output. Print one order and you can rebuild the tree (copy); another yields the nodes of a BST already sorted; a third gives you safe instructions for freeing memory (children before parents). That versatility is why traversals dominate this unit's question papers.

Euler tour — the generic method

View the tree as a directed graph and imagine walking counter-clockwise around its outline, starting and ending at the root, passing down every left edge and back up. Every node is touched once on the way down and once on the way up, so the tour records 2N − 1 vertex visits for N nodes. The three classic traversals are simply three different moments to write a node down during this one walk:

  • Preorder — record a node the first time you pass it (arriving from above).
  • Inorder — record a leaf the first time, an internal node the second time (after returning from its left subtree).
  • Postorder — record a node the last time you pass it (leaving toward its parent).

Example: for the tree 1(2(3,4)) the Euler tour is 1 2 3 2 4 2 1 — nine visits for five nodes (2·5 − 1). A second example, 1(5(4(2,3))), tours as 1 5 4 2 4 3 4 5 1. A useful side-fact: the left-to-right order of leaves is identical in all three traversals — only internal nodes move around.

The names come from where the node (root of each subtree) is processed: pre = before the subtrees, in = between them, post = after them. All three are the same recursion with a single line moved.

void preorder(node *T) {
    if (T != NULL) {
        printf("%c", T->data);      /* N */
        preorder(T->left);          /* L */
        preorder(T->right);         /* R */
    }
}
void inorder(node *T) {
    if (T != NULL) {
        inorder(T->left);
        printf("%c", T->data);      /* N between L and R */
        inorder(T->right);
    }

    if (T != NULL) {
        postorder(T->left);
        postorder(T->right);
        printf("%c", T->data);      /* N last */
    }
}
Why only three of the six permutations survive

With left-before-right convention there are six label orders: NLR, LNR, LRN, NRL, RNL, RLN. But NLR ≡ mirror of NRL, LNR ≡ RNL, LRN ≡ RLN — each pair visits the same nodes in mirror order. Keeping left first, only LNR (inorder), LRN (postorder), NLR (preorder) remain distinct. Inorder is additionally the only one that is naturally defined for binary trees: "between the two children" makes no sense for nodes with three-plus children.

Why write non-recursive versions?

Recursive traversal is short and clean, but every call consumes a hidden stack frame managed by the runtime. On very deep or skewed trees that invisible stack can overflow; an explicit stack you size and control removes that ceiling. An explicit stack also makes the traversal pausable and resumable — the foundation of iterators that yield one node at a time. And examiners simply love asking for the iterative form.

6.1 — Iterative preorder (stack)

Idea: the stack remembers "what is left to visit", doing exactly what the call stack did. Push the root. Then loop: pop a node, visit it, push its right child first, then its left — pushing right before left guarantees left pops first, preserving N→L→R.

preorder_iter.c
void preorderIter(Node* root) {
    if (root == NULL) return;
    Stack s; push(&s, root);
    while (!isEmpty(&s)) {
        Node* n = pop(&s);
        printf("%d ", n->data);          /* visit on POP   */
        if (n->right) push(&s, n->right);/* right FIRST    */
        if (n->left)  push(&s, n->left); /* left on top    */
    }
}

6.2 — Iterative inorder (stack)

One-line difference from preorder: in iterative preorder a node is visited before it is pushed; in iterative inorder a node is visited immediately after it is popped. Slide 1: dive left, pushing everyone you pass. Slide 2: pop → visit → jump to the popped node's right subtree and dive left again.

inorder_iter.c
void inorderIter(Node* root) {
    Stack s; Node* T = root;
    while (T != NULL || !isEmpty(&s)) {
        while (T != NULL) {          /* slide 1: go left, saving ancestors */
            push(&s, T);
            T = T->left;
        }
        T = pop(&s);                 /* slide 2: backtrack */
        printf("%d ", T->data);      /* visit AFTER pop */
        T = T->right;                /* then explore right subtree */
    }
}

6.3 — Non-recursive postorder (two stacks / flag method)

Postorder is the hardest to iterate because a node must wait until both subtrees are done. The course solution pairs each stack entry with a flag: flag NULL = "returning from the left, right side still pending", flag 1 = "right side visited, now safe to print". A node is pushed twice across its lifetime; the flag remembers which visit this is.

postorder_nonrec.c — flag-stack method (course version, cleaned)
void nonRecPostorder(node *T) {
    if (T == NULL) return;
    Stack S; FlagStack S1;                 /* parallel stacks */
    while (T != NULL) {                    /* descend left, flag 0 */
        push(&S, T);  pushF(&S1, NULL);
        T = T->left;
    }
    while (!isEmpty(&S)) {
        T   = pop(&S);
        int flag = popF(&S1);
        if (flag != NULL)                  /* second visit: right done */
            printf("%d ", T->data);        /* visit now */
        else {                             /* first visit: schedule right */
            push(&S, T);  pushF(&S1, 1);
            T = T->right;
            while (T != NULL) {            /* descend right subtree leftwards */
                push(&S, T);  pushF(&S1, NULL);
                T = T->left;
            }
        }
    }
}
Elegant alternative — two-stack reversal

Postorder is the reverse of "Node → Right → Left". So: push root onto S1; repeatedly pop from S1, push that node onto S2, and push its left then right children onto S1. When S1 empties, popping S2 yields exactly postorder. Two stacks, no flags — a favourite shortcut in MCQs.

6.4 — Level-order traversal (queue)

Breadth-first order needs the opposite discipline: instead of diving deep (stack = LIFO), we serve nodes in arrival order (queue = FIFO). Algorithm: enqueue the root; then repeatedly dequeue-and-print, enqueuing that node's children. Children of level k are fully enqueued before level k+1 is served.

levelorder.c
void levelOrder(Node* root) {
    if (root == NULL) return;
    Queue q; enqueue(&q, root);
    while (!isEmpty(&q)) {
        Node* n = dequeue(&q);
        printf("%d ", n->data);
        if (n->left)  enqueue(&q, n->left);
        if (n->right) enqueue(&q, n->right);
    }
}

Level-by-level printing (two-queue variant)

To print each level on its own line, keep two queues: q1 holds the current level, q2 collects children as q1 drains; then swap and repeat. The loop naturally terminates when a swap hands over an empty queue.

levelwise_twoqueues.c
void levelWise(Node* root) {
    Queue q1, q2;
    if (root == NULL) return;
    enqueue(&q1, root);
    while (!isEmpty(&q1)) {
        init(&q2);                       /* children of current level */
        while (!isEmpty(&q1)) {
            Node* T = dequeue(&q1);
            printf("%d ", T->data);
            if (T->left)  enqueue(&q2, T->left);
            if (T->right) enqueue(&q2, T->right);
        }
        q1 = q2;                         /* next level becomes current */
        printf("\n");
    }
}

6.5 — Rebuilding a tree from two traversals

Which pairs work? Inorder + Preorder or Inorder + Postorder determine a binary tree uniquely. Why: the first element of a preorder (or last of a postorder) is the root; the root then splits the inorder into the left and right subtrees; recurse. Preorder + Postorder alone is ambiguous (a single child could be a left or right child) — it works only if every internal node has 2 children and you accept that convention.

  1. Pick the root: first element of preorder / last element of postorder.
  2. Find that value in the inorder; everything left of it = left subtree's inorder, right of it = right subtree's inorder.
  3. Count those lengths and slice the same number of elements out of the preorder/postorder.
  4. Recurse on each (inorder-half, traversal-half) pair.

Section 07 · Part A

Binary Search Trees — Search, Insert, Build

Why we need a smarter tree

Searching an arbitrary binary tree means checking every node in the worst case — O(n), no better than a plain list, because knowing one value tells you nothing about where others hide. Binary search on a sorted array is fast precisely because one comparison rules out half the remaining elements — but arrays are hostile to insertion and deletion. The binary search tree bakes the binary-search rule into the shape of the tree itself: at every node, one comparison discards an entire subtree, yet the structure stays fully dynamic — linked nodes, pointer surgery, no shifting.

Definition — the BST property

A binary search tree is a binary tree in which every node N satisfies: every value in N's left subtree < N's value, and every value in N's right subtree > N's value. The condition holds at every node, not just the root — so every subtree is itself a valid BST. It is a recursive, self-similar rule: the same test applied at each level.

Two consequences follow immediately. First, shape is not unique — many different trees can hold the same set; only the ordering rule matters. Second, an inorder traversal of a BST emits the keys in ascending sorted order, for free — no comparisons, no extra work; this single fact is the most examined line in the whole unit. (Traverse right-node-left instead and you get descending order.)

7.1 — Searching

Idea: compare the target x with the root r. Equal → found. Smaller → by the property, x can only be in the left subtree; larger → only in the right. An empty subtree (NULL) reached while following the path means x is absent — and, as §7.2 shows, that exact NULL is where x would be inserted. Both member calls do constant work per node and recurse into one child, so the work follows a single root-to-node path: cost = O(height).

member_recursive.c
bool member(int x, Node* n) {
    if (n == NULL) return false;
    if (x == n->data) return true;
    if (x < n->data)
        return member(x, n->left);
    return member(x, n->right);
}

Search complexity

Search cost = O(height). Balanced tree of n nodes: O(log n). Skewed tree: O(n). Same statement covers insert and delete — all three follow one root-to-node path. With random insertion order the average path length satisfies P(n) ≤ 1 + 4·log₂n — within a constant factor of perfect balance, so on average all three operations are O(log n).

7.2 — Insertion

Idea: if the tree is empty the new node becomes the root; otherwise behave exactly like member. The search must eventually fall off the tree onto an empty NULL child — and that NULL is precisely where the new node belongs. A new node is therefore always attached as a leaf: insertions happen at terminal positions and never in the middle of a BST, and because the new leaf is placed as the correct child of its parent, the BST property survives automatically everywhere else.

  1. If the tree is empty, make the root point to the new node.
  2. Compare the data with the current node's data.
  3. Smaller → descend left; larger → descend right; repeat until a terminal node is reached.
  4. Attach the new node as the appropriate child of that terminal parent.
insert_recursive.c — pointer passed by reference
void insert(int x, Node** n) {
    if (*n == NULL) {              /* fell off the tree: attach here */
        *n = makeNode(x);
        return;
    }
    if (x < (*n)->data)
        insert(x, &(*n)->left);
    else if (x > (*n)->data)
        insert(x, &(*n)->right);
    /* x == (*n)->data : duplicate — do nothing (one convention) */
}

The Node** (pointer-to-pointer) is the trick that makes this code so compact: passing the address of the link field means the recursion can reach down and re-aim the parent's left/right pointer — or the tree's root itself — without any special-casing for an empty tree or leaf attachment.

7.3 — Minimum, maximum & duplicates

The BST property forces the minimum to the far left and the maximum to the far right: minimum = keep following left children from the root (a leftmost node has no left child, so nothing smaller can hang below it); maximum = mirror image, keep following right children. Both cost O(height).

minmax.c
int findMin(Node* n) {
    if (!n) return -1;            /* empty tree convention */
    while (n->left) n = n->left;
    return n->data;
}
int findMax(Node* n) {
    if (!n) return -1;
    while (n->right) n = n->right;
    return n->data;
}
Handling duplicates

The strict property (< and >) leaves duplicates homeless, so a convention is required. The three standard policies: (1) reject — insert() does nothing (the deck's code comment "already present: do nothing"); (2) count field — store a frequency counter in the node, no structural change; (3) consistently place equal keys in one side (commonly right subtree: insert left if x < data else right) — this keeps inorder stable but must be applied uniformly, or the tree's invariant becomes ill-defined. State the chosen policy in any answer involving duplicates.

Insertion order changes everything

Insert 1, 2, 3, …, n in sorted order and every key walks the right spine: the result is a skewed chain of height n − 1, and building it costs 1+2+…+n = O(n²) total with O(n) searches forever after. The same code fed a random order tends toward balance with O(log n) operations. Performance differences this dramatic, from input order alone, are the strongest argument for self-balancing trees (AVL/Red-Black) that come later in the course.

BST Deletion, Analysis & the Full ADT

7.4 — Deletion: the three cases

Deletion first locates the target exactly as member does. What happens next depends on how many children the doomed node has — and the difficulty climbs steeply with that count:

  1. Leaf (0 children) — deletion is trivial: make the parent point to NULL and free the node.
  2. One child — splice the node out: the parent adopts the node's only child directly.
  3. Two children — the tricky case: pulling the node out would orphan an entire subtree, so we never physically remove it. Instead we overwrite its value with its inorder successor and then delete that successor (which, by construction, falls into case 1 or 2).
Inorder successor — the safe replacement

The inorder successor of node x is the smallest value strictly greater than x. In tree terms: go right once (into the right subtree), then keep going left until no left child remains. Why it is safe: being the smallest value larger than x, it can sit in x's position while keeping everything on the left smaller and everything on the right larger — the BST property survives everywhere. And it always has at most one (right) child — a leftmost node cannot have a left child — so removing it is a case-1 or case-2 operation.

Case 1 — deleting a leaf

Case 2 — deleting a node with one child

Continuing (1 already gone), delete 2: its only child is 4, so 4 slides up into 2's place. The splice keeps every remaining value on its correct side because the promoted child moves up along its own parent link.

Case 3 — deleting a node with two children

Delete the root 6. Promoting a single child (say 2) is impossible — the other child's whole subtree {7, 8, 9} would be orphaned. So we find 6's inorder successor: right once to 8, then left to 7. 7 has no left child, so 7 is the minimum of the right subtree. Copy 7's value into the root, then delete the original node 7 (a leaf — case 1).

delete.c — deleteMin + delete, pointer-by-reference
/* Walk left to find AND unlink the smallest node; return its value. */
int deleteMin(Node** n) {
    if ((*n)->left == NULL) {
        int v = (*n)->data;
        *n = (*n)->right;        /* promote right child (may be NULL) */
        return v;
    }
    return deleteMin(&(*n)->left);
}

void delete(int x, Node** n) {
    if (*n == NULL) return;                          /* not found */
    if      (x < (*n)->data) delete(x, &(*n)->left);
    else if (x > (*n)->data) delete(x, &(*n)->right);
    else {                                           /* found it */
        if ((*n)->left  == NULL) *n = (*n)->right;   /* 0 or 1 child  */
        else if ((*n)->right == NULL) *n = (*n)->left; /* 0 or 1 child */
        else (*n)->data = deleteMin(&(*n)->right);   /* 2 children: copy successor */
    }
}

Read the two-child branch slowly: deleteMin(&(*n)->right) both returns the successor's value (which lands in the node's data field) and unlinks the successor node from its old position — two operations, one recursion. This is why the successor needs no special third deletion routine.

Deletion pointers examiners probe
  • The successor is always in the right subtree and is found by "right once, then left, left, left…". The inorder predecessor (rightmost of the left subtree) is an equally valid alternative replacement — some texts use it; mention both to show understanding.
  • When the successor replaces a two-child node, the successor's own right child (it has no left child) is adopted by its parent — never lost.

7.5 — Average vs worst case, and rival structures

If n elements arrive in random order, the first insertion becomes the root and splits the rest into a random left group and right group; the argument repeats recursively, yielding an average path length P(n) ≤ 1 + 4·log₂n — so on average, member / insert / delete all run in O(log n). But if elements arrive already sorted, every insertion walks the same direction and the tree degenerates into the skewed chain — O(n) per operation, O(n²) for n insertions. int leaf_nodes() {

Height / depth — recursive (deck version, height = edges)

height_rec.c
int height_rec(node *T) {
    if (T == NULL) return -1;              /* empty subtree: -1  */
    if (T->left == NULL && T->right == NULL)
        return 0;                          /* leaf: 0            */
    int l = height_rec(T->left);
    int r = height_rec(T->right);
    return (max(l, r) + 1);                /* taller side + 1    */
}
int height() { return height_rec(root); }

Note the conventions baked into the returns: NULL → −1 makes height count edges (leaf = 0, root alone = 0). If your course defines height as node-count, return 0 for NULL instead — but never mix conventions within one program.

Height — non-recursive (level counting)

The deck tracks the deepest stack reach during a stack-based walk; a cleaner equivalent counts levels with a queue: one BFS pass, +1 per level.

height_level.c
int height_level(Node* root) {
    if (!root) return -1;
    Queue q; enqueue(&q, root);
    int h = -1;
    while (!isEmpty(&q)) {
        int nodesAtLevel = size(&q);
        h++;                               /* entering a new level */
        while (nodesAtLevel--) {
            Node* n = dequeue(&q);
            if (n->left)  enqueue(&q, n->left);
            if (n->right) enqueue(&q, n->right);
        }
    }
    return h;
}

Section 08

Expression Trees

Definition & two labeling rules

An expression tree is a labeled binary tree representing an arithmetic expression under two rules: (1) every leaf is labeled by an operand and represents that operand alone; (2) every internal node is labeled by an operator θ — if its left child represents E₁ and its right child E₂, the node represents (E₁) θ (E₂). Rule 2 applied bottom-up gives every internal node its meaning automatically, and the tree's shape encodes the expression's structure so completely that no parentheses are needed to see which operator applies to which operands.

Traversals become notations — for free

This is the payoff promised in Section 06: listing the tree's labels (instead of node names) in each traversal order produces a famous way of writing the same expression:

8.1 — Building an expression tree from postfix (stack method)

Scan the postfix string left to right, maintaining a stack of subtrees:

  1. Read the expression character by character.
  2. Operand → push it as a one-node tree.
  3. Operator → pop two trees: the first pop becomes the RIGHT child, the second pop the LEFT child; push the merged operator tree.
  4. Repeat; when the input ends, exactly one tree remains on the stack — the expression tree.
Pop order trap

For non-commutative operators (−, /, ^) mixing up the two pops silently mirrors the tree: first popped = right, second popped = left. Writing "pop two operands" without the order is the most common lost mark in this topic.

8.2 — Evaluating an expression tree

Evaluation is a postorder traversal in disguise: to evaluate a node you must first evaluate its left subtree, then its right subtree, and only then apply the node's operator to the two results. A leaf evaluates to its own stored number. Children-before-parent is mandatory — which is exactly why postorder (L, R, N) is the natural fit and preorder/inorder are not.

evaluate.c
int evaluate(Node* n) {
    if (n->isLeaf) return n->value;          /* operand: base case */
    int L = evaluate(n->left);
    int R = evaluate(n->right);
    switch (n->op) {                          /* apply operator last */
        case '+': return L + R;
        case '-': return L - R;
        case '*': return L * R;
        case '/': return L / R;
    }
}

Huffman Coding — Optimal Prefix Compression

Huffman coding, invented by David A. Huffman, is a classic lossless data compression technique: it assigns shorter binary codes to more frequent characters and longer codes to rarer ones, so the encoded message shrinks without any information loss. The workflow for a body of text: count the frequency of every character → build a Huffman tree from the frequencies → read a code for each character off the tree → encode.

Fixed vs variable length encoding

Suppose a message is built from five characters a, b, c, d, e occurring with probabilities .12, .40, .15, .08, .25. A fixed-length code must give every character the same number of bits — ⌈log₂5⌉ = 3. A variable-length code spends fewer bits on the heavy hitters. Compare two schemes:

Average code length = Σ (probability × code length) — this is what actually determines compressed size. Code 1: every code is 3 bits → average 3.00. Concrete saving on a message: encoding bcbebc costs 6 × 3 = 18 bits under Code 1 but only 12 bits under Code 2.

The prefix property

A code is decodable without separators only if no character's code is a prefix of another's. Decoding then works by repeatedly "grabbing whichever prefix of the remaining bits is a legal code": e.g. 1101001 under Code 2 → 11 (b), leaving 01001 → 01 (c), leaving 001 (d) → "bcd", unambiguously. Without the property, one bit-string could decode to several messages. The property fails if you add E = 01 (0 becomes a prefix of it) or F = 10 (a prefix of 100, 1010…).

Why binary trees give prefix codes automatically

Map a code onto a binary tree: going left appends 0, going right appends 1; each leaf gets a character and the root-to-leaf path spells its code. A leaf is never on the path to any other node — so no code can be a prefix of another. Prefix codes correspond exactly to binary trees with characters at the leaves.

The algorithm — a greedy forest merge

  1. Count each character's frequency; make every character a one-node tree (a leaf) labeled with its frequency/weight. The collection is a forest.
  2. Select the two trees of smallest weight in the forest.
  3. Merge them under a new internal node whose weight = the sum of the two weights.
  4. Replace the two by the merged tree; repeat until one tree remains.
  5. Label left branches 0 and right branches 1; each character's code is the path from root to its leaf.

This is a greedy algorithm: at every step it makes the locally cheapest merge and never reconsiders — and the greedy choice is provably optimal. Intuition: merging the two least probable symbols first forces them deepest in the final tree, and code length equals depth — precisely where rare characters belong. The strategy guarantees no rare symbol ends up shallow (wasting the chance to shorten it) and no common symbol ends up deep (paying on every occurrence).

9.3 — Complexity & implementation sketch

With n symbols the forest starts with n one-node trees and shrinks by one per merge — exactly n − 1 merges. Using a priority queue (min-heap) keyed by weight makes "find the two smallest" an O(log n) operation (two extract-mins plus one insert per step):

total time = O(n log n)  ·  space = O(n)  ·  merges = n − 1
huffman.c — priority-queue sketch
void huffman(PriorityQueue* forest) {
    while (size(forest) > 1) {
        Node* t1 = extractMin(forest);     /* smallest        */
        Node* t2 = extractMin(forest);     /* second smallest */
        Node* merged = makeNode();
        merged->weight = t1->weight + t2->weight;
        merged->left  = t1;
        merged->right = t2;
        insert(forest, merged);            /* back into the forest */
    }
}

Decoding is the mirror image and famously fast: start at the root, read one bit at a time — 0 → left, 1 → right; hitting a leaf emits its character and resets to the root. No tables of variable-length matches, no backtracking — which is why Huffman decoding often outpaces encoding and suits low-latency streaming.

9.4 — Practical considerations & where it runs today

  • Code-table overhead: compressing one short string (like ABRACADABRA alone) can be a net loss — the decoder needs the code table, and shipping it can exceed the ASCII message. Huffman is practical when the encoded string is large relative to the table, or the table is pre-agreed (e.g. standard English letter frequencies).
  • Ties are free: equal weights may be merged in any order — different valid trees, same optimal average length. If your tree differs from a classmate's, both can be right.
  • Real deployments: the DEFLATE algorithm (ZIP, GZIP, Zlib, PNG) combines LZ77 dictionary coding with Huffman coding; JPEG Huffman-encodes quantised DCT coefficients; MP3 and AAC use Huffman tables for quantised audio data.
  • Why it stays popular: fast, simple decoding; low computational overhead; ideal for embedded and resource-constrained systems.
Section 10

Threaded Binary Trees

The waste that motivates threading

In the standard linked representation an n-node binary tree stores 2n child pointers, of which exactly n − 1 are non-NULL (every node except the root is pointed to once). That leaves n + 1 NULL pointers — more than half the pointer budget, sitting idle. A threaded binary tree recycles them: a NULL left child is replaced by a thread pointing to the node's inorder predecessor, and a NULL right child by a thread to its inorder successor. The payoff: traversal without any stack or recursion, in O(n) time and O(1) extra space.

Definition & node structure

Because a pointer field can now mean two things, each side carries a tag: tag = 0 → the pointer is a real child link; tag = 1 → the pointer is a thread to predecessor/successor.

threaded_node.c
struct tnode {
    int data;
    struct tnode *left, *right;
    int ltag, rtag;      /* 0 = child link, 1 = thread */
};

Types: a single-threaded tree threads only one side (commonly the right side — successor threads). A double-threaded / inorder-threaded binary tree (ITBT) threads both sides — this is the syllabus's "inorder threaded binary tree". Many textbook implementations also hang the whole tree from a dummy header node: the tree's root is the header's left child, and threads that "run off" the ends point back to the header, which gives every thread a valid target and simplifies boundary logic.

10.1 — Inorder traversal of an ITBT (no stack, no recursion)

Strategy: find the leftmost node (follow real left links while ltag = 0). Then repeat: visit; if the right side is a thread (rtag = 1) it already points at the successor — follow it directly; if it is a real child, move into that right subtree and again find its leftmost node.

inorder_threaded.c
tnode* leftmost(tnode* n) {
    while (n != NULL && n->ltag == 0)   /* 0 = real child */
        n = n->left;
    return n;                            /* leftmost (or thread-landing) */
}
void inorderThreaded(tnode* root) {
    tnode* T = leftmost(root);
    while (T != NULL) {
        visit(T);
        if (T->rtag == 1)
            T = T->right;                /* thread = successor, jump! */
        else {
            T = T->right;                /* real right subtree */
            T = leftmost(T);             /* its leftmost node */
        }
    }
}

10.2 — Preorder traversal of an ITBT

Strategy: preorder wants Node → Left → Right. From the current node: descend to the real left child if one exists; else take the real right child if one exists; else (a leaf) climb right-threads until you reach a node with a real right child and step into it. The climb works because the first ancestor with a real right child is exactly where preorder resumes after finishing a left subtree.

preorder_threaded.c
void preorderThreaded(tnode* root) {
    tnode* T = root;
    while (T != NULL) {
        visit(T);
        if (T->ltag == 0)
            T = T->left;                     /* N: real left child first */
        else if (T->rtag == 0)
            T = T->right;                    /* no left: real right child */
        else {
            while (T != NULL && T->rtag == 1)
                T = T->right;                /* leaf: climb threads upward */
            if (T != NULL)
                T = T->right;                /* step into first real right child */
        }
    }
}

Threading a tree (how the threads get built)

Threads are installed during one ordinary iterative inorder walk: keep the previously visited node; when the current node's left is NULL, set its left thread to prev (ltag = 1); when prev's right is NULL, set its right thread to the current node (rtag = 1). One pass, O(n).

Advantages
  • Traversal needs no stack and no recursion — O(1) auxiliary space.
  • No stack overflow on deep/skewed trees.
  • Direct O(1) access to inorder predecessor/successor of any node.
  • Every NULL pointer becomes useful information.
Disadvantages
  • Two tag fields per node — extra memory and branching in every routine.
  • Insertion/deletion must maintain both links and threads — more corner cases.
  • Threads are order-specific: an inorder-threaded tree supports inorder/preorder walks but not direct postorder.
  • Slightly harder to debug — a thread and a child look identical if tags are wrong.
Section 11

Heaps — the 5-Minute Scan

A heap is a complete binary tree (the shape that makes arrays work, §04) that additionally satisfies the heap property: in a min-heap every child's value ≥ its parent's; in a max-heap every child's value ≤ its parent's. Consequently the smallest (or largest) element always sits at the root — which is why heaps are the standard implementation of priority queues. Note the contrast with a BST: a heap only promises parent-vs-child ordering, not left-vs-right, so an inorder traversal of a heap yields no useful order.

Because the tree is complete, storage is a plain array with no gaps: node at index i has children at 2i+1 and 2i+2, parent at ⌊(i−1)/2⌋ (§04's formulas doing real work). Operations at a glance: insert = append at the end, then bubble up while it beats its parent — O(log n); extract-min/max = take the root, move the last element to the root, sift it down — O(log n); peek = O(1). Where you will meet heaps again: priority queues, heapsort, Dijkstra — and Huffman's algorithm, which needs exactly "give me the two smallest" machinery.

Section 12

Applications: Decision Trees & File Systems

The unit closes by showing that the two flagship applications are nothing new — just the terminology and traversal ideas from Sections 03–06, spotted in the wild.

12.1 — Decision trees

Definition

A decision tree uses each internal node as a question or test, each branch as an answer, and each leaf as a final outcome. Starting at the root and answering one question at a time, you walk a single path down to exactly one leaf — your decision. It is literally "the path from root to a node" (Section 03) put to work.

Why the shape fits: a decision process is inherently a sequence of narrowing choices — exactly what a root-to-leaf path is. Each question's answer determines the next question (parent→child branching), and the depth of a leaf counts the questions needed to reach that outcome — a natural measure of how expensive that decision is. You already know three places these live: expert systems (early AI encoded expertise as if/then trees — medical diagnosis, troubleshooting guides), machine-learning classifiers (a learned tree asks "is feature X above threshold Y?" to split data), and everyday business logic — eligibility rules, pricing tiers and "press 1 for…" phone menus are decision trees in disguise.

12.2 — File systems are literal trees

The file system root is the tree's root; directories are internal nodes; files are leaves; a directory "contains" its children exactly as a parent contains its children. Unlike a decision tree the branching factor is unbounded — a directory may hold any number of entries — so this is a general tree (stored, naturally, via the left-child right-sibling trick of §04).

  • A file path is a root-to-node walk: /home/ana/notes.txt spells the path — every / is one more edge down the tree.
  • Directory listing / find = preorder traversal: visit (print) the directory, then recurse into each child.
  • Folder size (du / disk usage) = postorder: a directory's total depends on its children's totals being known first — children before parent, precisely postorder's contract.
  • Search path resolution, DNS, DOM all inherit the same hierarchy + traversal reasoning.

14.6 — Prove the node bound (deck Practice 6)

Prove: a binary tree of height h has at most 2h+1 − 1 nodes, with equality exactly when the tree is perfect.

Solution

Level i can hold at most 2i nodes (i = 0 at the root), since each node has ≤ 2 children and the bound doubles per level. Summing levels 0 through h: 2⁰ + 2¹ + … + 2ʰ = 2h+1 − 1 (geometric series). Equality holds exactly when every level is completely full — which is the definition of a perfect tree. ∎

Section 15

60-Second Rapid Revision

Twenty-five one-liners. If any answer takes more than a heartbeat, jump back to its section.

01 · Linear vs non-linear?

Linear: one-to-one, single sequence (array/list/stack/queue). Non-linear: one-to-many & many-to-many (tree, graph).

02 · Tree definition in one line

Connected acyclic structure, one root, exactly one path root→any node; N nodes ⇒ N−1 edges.

03 · Depth vs height

Depth: edges down from root to node (root = 0). Height: edges down to farthest leaf (leaf = 0).

04 · Degree of node vs tree

Node: its child count. Tree: max degree over all nodes.

05 · Forest

Collection of disjoint trees; delete a root → forest of its subtrees.

06 · Max nodes on level i / height h

2i per level; 2h+1 − 1 total for height h (edges convention).

07 · Full vs complete vs perfect

Full: 0-or-2 children. Complete: levels filled left→right, last may be partial. Perfect: full + all leaves equal depth (2h+1−1 nodes).

08 · Strictly binary leaf count

n₀ = n₂ + 1; total nodes 2n₂ + 1 (always odd).

09 · Array formulas (0-indexed)

left = 2i+1, right = 2i+2, parent = ⌊(i−1)/2⌋. Great for complete trees, wasteful otherwise.

10 · General tree → binary tree

Left-Child Right-Sibling: left = first child, right = next sibling; root ends with no right child.

11 · The three DFS orders

Preorder N-L-R (copy, prefix) · Inorder L-N-R (sorted BST, infix) · Postorder L-R-N (delete, postfix, du).

12 · Why only three traversals?

Six permutations exist but NLR↔NRL, LNR↔RNL, LRN↔RLN are mirrors; keeping left-first leaves three.

13 · Iterative preorder vs inorder

Preorder: visit before push. Inorder: visit after pop. Both use a stack; level-order uses a queue.

14 · Non-recursive postorder trick

Flag-stack method, or two-stack reversal (N-R-L then reverse). Pre/post alone rebuild a tree only if every internal node has 2 children.

15 · Rebuilding from traversals

Inorder + preorder (root first) or inorder + postorder (root last) → unique tree. For a BST, preorder alone suffices.

16 · BST property

At every node: entire left subtree < node < entire right subtree — recursively, at every level.

17 · BST complexity

Search/insert/delete = O(height): O(log n) average (random insertions), O(n) skewed (sorted input → O(n²) build).

18 · BST insertion position

Always at a leaf/terminal node — the NULL where the search falls off. Never in the middle.

19 · BST deletion, two children

Replace value with inorder successor (right once, then leftmost — has ≤1 child), then delete the successor.

20 · Min & max of a BST

Min = leftmost node, max = rightmost; both O(height).

21 · NULL pointers in a linked BT

n + 1 of 2n links — the surplus that threading recycles.

22 · Threaded tree traversal

Inorder ITBT: thread (rtag=1) = jump to successor; real child = go right then leftmost. Preorder: left child, else right child, else climb threads to first real right child.

23 · Expression tree ↔ notations

Preorder → prefix · Inorder → infix (needs parens) · Postorder → postfix; evaluation = postorder; build from postfix: first pop = RIGHT child.

24 · Huffman essentials

Greedy merge of two smallest weights; n − 1 merges; O(n log n) with a priority queue; prefix property guaranteed by leaves; ties broken arbitrarily.

25 · Applications one-liner

Decision tree: depth of leaf = questions asked. File system: path = root-to-leaf walk; find = preorder; du = postorder; DEFLATE/JPEG/MP3 embed Huffman.
